第 1 部分

一个程序，几个文件

从这一部分起，程序不再是一个文件。五课只回答两件事： 为什么要拆、拆分之后各部分如何对应。 新教的只有三样：#include 的实际作用、头文件（承诺）和 .cpp（兑现）的分工、一次编几个文件。 学完你会认得那条最常见的链接错误，并且知道它在说什么。

1.1为什么不能都写在一个文件里

这一部分从一份作业说起。它读入 10 个分数，输出一张统计表。

先看一份能运行的

文件叫 1.1-all-in-one.cpp，八十几行，一个 main 从头管到尾。向下阅读，先感受一下长度： 

#include <cstdio>
#include <iostream>
#include <vector>

int main() {
    // 十个分数，一个一个读进来
    std::vector<int> scores(10);
    for (int i = 0; i < 10; i++) {
        std::cin >> scores[i];
    }

    // 总分、最高、最低：一遍扫完
    int total = 0;
    int top = scores[0];
    int low = scores[0];
    for (int i = 0; i < 10; i++) {
        total = total + scores[i];
        if (scores[i] > top) {
            top = scores[i];
        }
        if (scores[i] < low) {
            low = scores[i];
        }
    }

    // 平均分：又单独扫了一遍
    int totalAgain = 0;
    for (int i = 0; i < 10; i++) {
        totalAgain = totalAgain + scores[i];
    }
    double avg = totalAgain / 10.0;

    // 五档各几个
    int excellent = 0;
    int good = 0;
    int fair = 0;
    int pass = 0;
    int fail = 0;
    for (int i = 0; i < 10; i++) {
        if (scores[i] >= 90) {
            excellent++;
        } else if (scores[i] >= 80) {
            good++;
        } else if (scores[i] >= 70) {
            fair++;
        } else if (scores[i] >= 60) {
            pass++;
        } else {
            fail++;
        }
    }

    // 输出统计表
    printf("分数    ");
    for (int i = 0; i < 10; i++) {
        printf("%4d", scores[i]);
    }
    printf("\n");
    printf("总分    %4d\n", total);
    printf("平均    %4.1f\n", avg);
    printf("最高    %4d\n", top);
    printf("最低    %4d\n", low);
    printf("优      %4d\n", excellent);
    printf("良      %4d\n", good);
    printf("中      %4d\n", fair);
    printf("及格    %4d\n", pass);
    printf("不及格  %4d\n", fail);

    return 0;
}

输入是十个分数，一行，用空格隔开： 

92 85 77 60 58 100 73 88 95 64

编译并运行它： 

g++ -Wall 1.1-all-in-one.cpp -o all-in-one
./all-in-one < 1.1-all-in-one.in
分数      92  85  77  60  58 100  73  88  95  64
总分     792
平均    79.2
最高     100
最低      58
优         3
良         2
中         2
及格       2
不及格     1

结果是对的。这份程序能编译通过、运行结果正确，每一句单看都没毛病。 问题不在对错。

它的问题在哪里

问题在于它无法继续扩展。四个毛病，一个比一个具体：

  1. 四项功能集中在一个函数里。读输入、算总分最高最低、分档、输出统计表—— 四件事，中间只有四行 // 注释当路标。 你哪天想找「平均分是怎么算的」，得从七十行里把它找出来。
  2. 名称冲突。文件里有个变量叫 totalAgain。 为什么会有这么个名字？因为 total 已经用过了——想再算一遍总分， 一个函数里名字不能重复，只能命名为 totalAgain，把那段循环又写了一遍。 同一件事算两遍，只因为一个名字被占了。
  3. 无法单独测试一部分。想验证「分档」那一段是否正确，只能把整份程序运行一遍、 把十个分数输入进去，再从整张表里辨认哪几行是它计算的结果。 要测试一小部分，就得运行整个程序——这个问题往后会越来越严重。
  4. 修改一句，整份代码都要重新编译。这一条到 1.4 会用实际测量结果说明。

八十几行还不算多。工程里的文件是两千行——上面这四条会跟着放大几十倍： 名称冲突不只一处，而是大量出现；找一段代码靠搜索；改一行，整个团队都需要等待重新编译。

拆分后的结构

1.3 会把这份程序拆成三个文件。拆分之后那个目录的结构如下： 

cd 示例代码/1.3-两个文件
ls -1
构建.txt
main.cpp
main.in
stats.cpp
stats.h

三个文件的分工如下：

  • stats.h——承诺。只写「有哪些函数、各接受什么参数、各返回什么」， 一句实现都没有。谁想用这些函数，把这份声明插入文件开头即可。
  • stats.cpp——兑现。承诺过的每一个函数，在这里写出实现。
  • main.cpp——使用。只剩三步：读入、计算、输出。

四个问题就是这样解决的：每块活一个函数，名字各归各的（totalAgain 这个名字会消失）；要测试哪一部分，就编译哪一部分；修改一个文件，只重新编译那一个。

怎么做到的，是 1.2 到 1.4 的事。这一课先记住那张表的形式—— 拆分之后运行输出仍然是同一张表，一个字符都不差。

1.2#include 到底做了什么

0.2 那一课说过一句：#include 的作用就是把那个文件从头到尾复制一遍， 插入这个位置。这一课要讨论的是这句话的后半部分——重复包含会怎么样。

就是原样插入

先看个证据。下面这份 util.h 里有一个函数，不只有声明，连函数体都在： 

int twice(int x) {
    return x * 2;
}

再看用它的人——main.cpp 里，这个头文件被 #include 了两次： 

#include "util.h"
#include "util.h"

#include <iostream>

int main() {
    std::cout << twice(21) << std::endl;
    return 0;
}

（双引号那种是给「自己写的头文件」用的，尖括号那种是给标准库用的。区别到附录里说。）

这两行 #include 不是「使用一下」，是插入。 编译器读到的其实是这个： 

int twice(int x) {
    return x * 2;
}
int twice(int x) {
    return x * 2;
}

#include <iostream>
...

同一个函数，出现在同一个文件里两次。编译器当然不让。

重复包含：直接运行一次

上面那两份文件就在课里（1.2-重复包含-err 那个目录），编译一下： 

g++ -Wall main.cpp -o twice
In file included from main.cpp:2:
util.h:1:5: error: redefinition of ‘int twice(int)’
    1 | int twice(int x) {
      |     ^~~~~
In file included from main.cpp:1:
util.h:1:5: note: ‘int twice(int)’ previously defined here
    1 | int twice(int x) {
      |     ^~~~~

读那行：「twice 重复定义了」。 下面那条 note 指出第一次定义的位置。

上面那句 In file included from main.cpp:2 说的是 「这段内容是从 main.cpp 第 2 行那个 #include 插入的」—— 它甚至记录了是哪一次包含的。这就是「原样插入」最直接的证据。

别纠结行号

报错里的行号指的是课里那份文件。你自己输入的那份少开头那几行注释， 行号会小一点——关注它指出的问题，不要和那个数字纠缠。 往后每次列出的报错都是这样。

卫士：挡住第二次

真写代码的时候，谁也无法确定一个头文件会被包含几遍——你 #include 了它， 你 #include 的另一个头文件里可能也 #include 了它。 所以头文件都必须能处理「第二次包含」。

办法是在文件开头和结尾各加一段： 

#ifndef TWICE_H
#define TWICE_H

int twice(int x) {
    return x * 2;
}

#endif

三行，读法是：

  • #ifndef TWICE_H——「如果没定义过 TWICE_H 这个名字， 下面到 #endif 为止的都算数」
  • #define TWICE_H——「现在给你定义上」
  • #endif——「到此为止」

第二次包含的时候，TWICE_H 已经定义过了， #ifndef 那行不成立，整段直接被跳过—— 等于第一次进来以后，后面几次都是空的。包含几遍结果都一样。

这个机制有一个名字，叫头文件卫士（guard）。 那三行本身不是代码，是给预处理器看的指令，末尾没有分号。 TWICE_H 这个名称可以任意指定，但全工程不能重——习惯上跟着文件名走。

例题 · 加了卫士的那一份

课里有个目录叫 1.2-卫士，文件和刚才那个 -err 目录一模一样，只多了那三行： 

#ifndef TWICE_H
#define TWICE_H

int twice(int x) {
    return x * 2;
}

#endif

还是那个「重复包含」的 main，这次编译通过，运行结果也正确： 

g++ -Wall main.cpp -o guard
./guard
42

两份文件的差别就是那三行。一份报重复定义，一份输出 42。

还有一种写法：把三行换成一行 #pragma once，意思一样， 现在的编译器都认。老代码里两种都能见到，能够认出即可。

两个文件都包含同一份

卫士解决的是「一个文件里重复包含」。还有另一种情况，它无法处理。

假如工程里有两个 .cpp，都 #include 了同一个头文件 （这是常事）。卫士保证每个文件里只包含一遍——但两个文件各包含一遍， 合起来就是两份定义。

课里也有这一份，目录叫 1.2-重复定义-err：两个源文件， 都包含了那个 util.h。 编译分两步进行： 

g++ -Wall -c main.cpp -o main.o
g++ -Wall -c other.cpp -o other.o
g++ main.o other.o -o dup-def

前两条没有输出任何内容就通过了——每个文件单独看都是正确的。 第三条失败： 

/usr/bin/ld: other.o: in function `twice(int)':
other.cpp:(.text+0x0): multiple definition of `twice(int)'; main.o:main.cpp:(.text+0x0): first defined here
collect2: error: ld returned 1 exit status

这次报错的不是编译器，是链接器（ld）—— 它要把这两个 .o 合成一个程序，一数：twice 有两份。

两句话：multiple definition of twice（twice 定义了不止一次）、 first defined here（第一份在 main.o 那边）。 谁先谁后看你链接时的顺序，看的是「谁重了、另一个在哪儿」。

所以头文件里到底能放什么

这一课两种错误，原因是一样的：头文件里放进了函数的定义——带函数体的 那种。卫士挡得住「同一个文件里重复包含」的；刚才链接器报告的问题，它挡不住。

头文件里该放的是声明：函数的名字、参数和返回类型，末尾一个分号， 不写函数体。声明出现多少遍都没事，只要每遍说的是同一件事；一个函数的 定义，全程序只能有一份——同一份文件里多出第二份，编译器报 redefinition；两个文件各一份，链接器报 multiple definition。

下一课整课都在做这件事：声明留在 .h，函数体移到某一个 .cpp。

练习

练习 1-3

一个文件里，同一个函数写两遍——就当作是被包含了两遍：

    return x * 2;
}

int twice(int x) {
    return x * 2;
}

int main() {

编译一下，把报错复制到答案里核对。重点不是把它改对， 是看清编译器说的那句 redefinition—— 往后你在别的项目里遇到它，需要直接认出这是「重复包含」。

看答案

程序就是练习里那一份，一个字符没有改动——这一份要的就是它无法编译： 

#include <iostream>

int twice(int x) {
    return x * 2;
}

int twice(int x) {
    return x * 2;
}

int main() {
    std::cout << twice(21) << std::endl;
    return 0;
}

编译器输出的内容，一字不差地复制在这里：

1-3-err.cpp:14:5: error: redefinition of ‘int twice(int)’
   14 | int twice(int x) {
      |     ^~~~~
1-3-err.cpp:10:5: note: ‘int twice(int)’ previously defined here
   10 | int twice(int x) {
      |     ^~~~~

一条 error，底下那条 note 提供辅助—— 指出第一次定义的位置。

  • 14:5——第 14 行、第 5 个字符，也就是后一个 twice。它报告的是重复的那一个。
  • 10:5——第一次定义的位置。对照着数一下： 第 10 行和第 14 行各有一个 int twice(int x)， 中间隔着三行。
  • redefinition——重复定义。看见这个词， 第一反应就是「同一个内容是不是被插入了两遍」。

这就是 1.2 那个真实案例的同一个问题：那边是头文件被包含了两遍， 这边是手动编写了两遍——编译器看来完全相同。

（课里那条报错前面还有一句 In file included from main.cpp:2:； 这一份是单文件，没有那一句。多出来的那句不是重点， error 那行才是。）

练习 1-4

现在换个写法，让它能够编译通过、并且输出 42：同名函数声明两遍、定义只留一份。 

int twice(int x);
int twice(int x);

int twice(int x) {
    return x * 2;
}

上面这两行只是函数声明——有个返回类型、有个名字和参数表， 末尾一个分号，没有函数体。这叫声明：只是在说 「有这样一个函数，形式如此」，没有说明它做什么。 

42

做完这题你就明白卫士挡的是什么了：它阻止的是重复定义。 声明多包含几遍，编译器不会给出任何提示。

看答案

声明两遍、定义一遍：

#include <iostream>

int twice(int x);
int twice(int x);

int twice(int x) {
    return x * 2;
}

int main() {
    std::cout << twice(21) << std::endl;
    return 0;
}

运行输出 42。

声明写几遍，编译器不会有任何提示。因为它记录的是同一件事： 「存在一个名为 twice 的函数，接受 int、返回 int」—— 记录两遍仍然是同一件事。定义不同：那是「具体实现」， 两份做法放在一起，它无法确定该用哪一份定义，就报 redefinition。

回头再看 1.2 的包含卫士，它阻止的是什么就清楚了：阻止的是定义。 头文件里真只剩函数声明的话，包含两遍确实没有问题——可 struct、class 那种定义是不能重复的， 卫士挡的主要就是它们。所以通常的规则是：头文件一律添加包含卫士， 不要考虑这一份里到底有没有定义。

你现在能写什么：你能说清 #include 是「原样插入」， 并且知道两种「由重复包含造成的错误」分别是什么形式——同一文件里包含两遍（ redefinition，编译器报告的）和两个文件各包含一遍 （multiple definition，链接器报告的）。 下一课给头文件派个正经活：只放声明。

1.3声明和定义

基础课讲过一条规矩：要用一个函数，先定义它——所以函数都写在 main 上面。这一课要把这条规矩改一个字。

头文件里放承诺

上一课那个错误，根子是「函数的定义被包含了两遍」。 避免它的办法很直接：头文件里只放声明，一个函数体都不放。

声明和定义的分工，用一句话说：

  • 声明是承诺：有这样一个函数，名称如此，接受这些参数、返回那个值。 末尾是分号，没有函数体。
  • 定义是兑现：函数体在这儿，工作是这么做的。 一个程序里，每个函数只能兑现一次。

声明可以出现在多处——出现几遍都可以，编译器能识别出它们是同一个声明。 兑现只许有一处。

于是基础课那条规矩要改一个字： 

要用它，先定义它。      ← 基础课（都在一个文件里，函数写在 main 上面）

要用它，先声明它。      ← 从现在起（定义在别的文件里，看不见）

你用的每一个标准库函数，都是这么办的：std::cout 在 <iostream> 里被声明，定义在标准库里， 找不找得到是链接器的事（0.2 那一课看到过它怎么查找）。

第一个多文件程序

把 1.1 那份拆分后就是三份文件。先查看头文件—— 它只有声明，没有函数实现： 

#ifndef STATS_H
#define STATS_H

#include <vector>

// 读 n 个分数回来
std::vector<int> readScores(int n);

// 平均分
double average(std::vector<int>& scores);

// 输出统计表：分数、总分、平均、最高、最低、五档各几个
void printReport(std::vector<int>& scores);

#endif

三行承诺，末尾都是分号。卫士那三行（1.2 讲的）照写在第一行和最后一行。

再看兑现的那份，stats.cpp： 

#include "stats.h"

#include <cstdio>
#include <iostream>

    ...（1.1 里「算总分最高最低」「五档各几个」「输出统计表」那三段，全部移到这里）...
}

第一行 #include "stats.h" 不是为了给别人用， 是给自己核对：把声明包含进来，编译器就会一句一句比—— 名字、参数、返回类型，和承诺对不上的，立即报告出来。

（上面那个 ... 是简化写法。整份文件一字不差地放在 1.3-两个文件 那个目录里，你需要输入的就是它。）

最后是用它的那份，main.cpp——从七十行变成七行： 

#include "stats.h"

int main() {
    std::vector<int> scores = readScores(10);

    printReport(scores);
    return 0;
}

readScores 和 printReport 这两个名字， 编译器在 stats.h 里读取到声明——知道它们接受什么参数、返回什么值， 所以敢让你调用。至于它们到底在哪儿、是谁写的，那是链接器的事（1.5 讲）。

和 1.1 比一比

拆完这个目录，按照 构建.txt 输入两行： 

g++ -Wall main.cpp stats.cpp -o report
./report < main.in

输出的表，和 1.1 那份完全相同——这不是口头说明，而是实际对比得到的 （../all-in-one 是 1.1 那个编译出来的程序，.. 是上一层目录）： 

diff <(../all-in-one < ../1.1-all-in-one.in) <(./report < main.in)
（没有任何输出）

diff 是个比对两个文件/两段输出的工具， 一样就没有任何输出。没有输出，说明两份输出一个字节都不差。

拆分文件不改变结果。这句话往后还会出现很多次—— cmake、库、工程，都是「换一种组织方式，程序仍然是同一个程序」。

那个没写的 #include

回头看 main.cpp。它在第五行以前就用了 std::vector，可是它自己没写 #include <vector>。 为什么能够编译通过？

因为 stats.h 里有那一行，而 stats.h 被插入了 —— 插入的是内容，内容里附带的 #include 当然也跟着插入。 这就是 1.2 那句话的又一次体现。

能编译通过不等于应当这样写

上面那份是故意的，为了说明「包含」有多彻底。 真写代码的时候规矩是谁用谁 include：main.cpp 自己用 vector，就自己写一行 #include <vector>。

不这么写会出什么事：哪天 stats.h 里不再需要 vector， 那行被删掉，main.cpp 就突然无法编译了——而它的作者什么都没改。

1.4一次编译几个文件

1.3 那两行命令里，g++ 一次接受两个 .cpp。 它在中间执行了什么？这一课把它拆开分析。

一条命令拆成三条

课里有个目录叫 1.4-分开编，里面的文件和 1.3 那个目录一模一样， 只有 构建.txt 换了一种写法： 

g++ -Wall -c main.cpp -o main.o
g++ -Wall -c stats.cpp -o stats.o
g++ main.o stats.o -o report

第一行的 -c 是 0.2 看到过的那个：编译到 .o 就停止，不链接。 前两行各处理一个文件，第三行把两个 .o 交给链接器。

运行完之后目录里多了三个文件，大小是这样： 

wc -c main.o stats.o report
 6920 main.o
22432 stats.o
23888 report
53240 总计

（wc -c 是数字节。这几个数不用记，也不用研究哪个比哪个大—— 从文件大小倒推不出程序在干什么，这话第 0 部分说过。）

运行结果同样是那张表。-c 分开编译，与用一条命令编译完成， 生成的程序相同。

改一个文件，只重新编译那个

那为什么要分？因为分开之后就能只重新编译修改过的那个。 实际试验一下——把 stats.cpp 里平均分那一行修改一下 （%4.1f 改成 %5.2f，小数多输出一位），然后只重新编译它： 

g++ -Wall -c stats.cpp -o stats.o
g++ main.o stats.o -o report

看两个 .o 的时间（ls -l 的第六第七列，时间和文件名）： 

ls -l --time-style=+%H:%M:%S main.o stats.o | awk '{print $6, $7}'
09:17:11 main.o
09:17:37 stats.o

（ls 是按名字排的，不是按时间，所以 main.o 排到了前面—— 顺序别管，看那两个时间。）

main.o 仍然是原来的时间（没有重新编译），stats.o 是新的。 输出也跟着变了：平均 79.20。

这就是分开编译的意义：修改一个文件，只重新编译那一个。 工程一大，这一步省下的是几分钟到几十分钟。

你的时间当然跟我这儿不一样

上面那两个时间是这台机器上的。你实际运行时得到的是你自己的时间—— 要看的不是数字，是两个时间不一样：一个是旧的、一个是新生成的。

例题 · 链接就是把 U 和 T 对应起来

0.2 那一课用 nm 看过：.o 里有些名字带 U，意思是「需要使用，但它不在当前文件中」。现在有两个 .o 了，正好看看它是怎么被补上的。

先看 main.o 里缺少什么符号（-C 仍然是那个「把经过修饰的名称 还原为可读形式」）： 

nm -C main.o | grep ' U '
                 U __gxx_personality_v0
                 U __stack_chk_fail
                 U _Unwind_Resume
                 U readScores(int)
                 U printReport(std::vector<int, std::allocator<int> >&)
                 U operator delete(void*, unsigned long)

六条。头三条和最后一条是编译器自己添加的（异常处理、栈保护、 内存回收——-Wall 一直开启的内容），跟我们写的代码没有关系，暂时不管。 中间那两条才是我们的，正是 main.cpp 调用过、 却只看到过声明的那两个函数。

再看 stats.o 里拿出来的（T 是「我这儿有」）： 

nm -C stats.o | grep ' T '
0000000000000000 T readScores(int)
00000000000001ba T printReport(std::vector<int, std::allocator<int> >&)
0000000000000114 T average(std::vector<int, std::allocator<int> >&)

一个缺少定义、一个正好提供定义。链接器执行的操作就是把这两份符号表对应起来。 对应之后的程序里，那两个名称从「缺少定义」变为具有地址： 

nm -C report | grep -E 'readScores|printReport'
00000000000014bd T readScores(int)
0000000000001677 T printReport(std::vector<int, std::allocator<int> >&)

（stats.o 里那个 average 没出现在 main.o 的符号表上——因为 main.cpp 没有直接调用它， 是 printReport 在内部使用的。需要哪个符号、提供哪个符号，取决于调用关系。）

下一页（1.5）要报的那条错误，就是这两份符号表无法对应的时候—— 有引用，但没有定义。

分开编译很方便，但有一个代价：你得自己记着谁改过。

刚才那个「只重新编译 stats.o」是我手动执行的——我知道自己改了 stats.cpp。文件变成五个、十个呢？改完之后：

  • 哪些 .o 需要重新编译？
  • 哪个头文件改了，意味着所有包含过它的 .cpp 都要重新编译？
  • 顺序呢？先链接还是先完成编译？

这三件事人无法长期承担。第 2 部分整个就是讲「把这些工作交给构建工具」—— 你只要告诉它「程序由哪几个文件编译成」，剩下的由它自动计算。

但那一课的前提是这一课：构建工具也按照这三步执行， 你认得那三步，它输出的内容你才能读懂。

    printf("最低    %4d\n", low);
    printf("优      %4d\n", excellent);
    printf("良      %4d\n", good);
    printf("中      %4d\n", fair);
    printf("及格    %4d\n", pass);
    printf("不及格  %4d\n", fail);
}

int main() {
    std::vector<int> scores = readScores(10);

    printReport(scores);
    return 0;
}

三件事的答案：

  • 一、第一条 -c 只编译不链接，产出 1-7.o；第二条把这个 .o 交给链接器， 产出可执行文件。
  • 二、这台机器上测量得到：.cpp 约 3 KB、 .o 约 22 KB、可执行文件约 23 KB。 你那几个数可能不同，观察大致范围即可。.o 比源文件大得多—— 里面不只是你写的那些代码（1.4 那个例题用 nm 看过它装的是什么）。
  • 三、两步都必须重新执行。.o 是「这个文件的编译结果」， 源文件修改一个词，它就会过期；链接那一步也必须重新执行，否则装入程序里的 还是旧的那个 .o。

（程序要是拆成两个 .cpp，第三条的答案就变了： 修改过的那一个重新编译，另一个保持不变，最后链接一次——这就是 1.4 正文里 那组时间戳。分开编译节省的时间，到那里才能体现。）

你现在能写什么：你能把「一条命令」拆成「一次编译一个、最后链接」， 能说明分开编译是为了减少重新编译的时间，也知道应当由构建工具记录这些关系。

1.5链接错误长什么样

声明了、写好了、也编译过了——但程序仍然无法生成。 这一课要演示的就是这种：能够编译通过，但链接失败。

直接运行一次

课里那个目录叫 1.5-少链接-err：三个文件和 1.2 的 重复定义 那个目录看上去一样，只有 构建.txt 是错的—— 它编译了 main.cpp，遗漏了编译 stats.cpp： 

g++ -Wall -c main.cpp -o main.o
g++ main.o -o report

第一行顺利通过。第二行： 

/usr/bin/ld: main.o: in function `main':
main.cpp:(.text+0x29): undefined reference to `readScores(int)'
/usr/bin/ld: main.cpp:(.text+0x35): undefined reference to `printReport(std::vector<int, std::allocator<int> >&)'
collect2: error: ld returned 1 exit status

undefined reference to ...——未定义的引用。 往后你会经常看见它，每次的意思都一样：有符号被引用，但没有定义。

一句一句读

这种报错篇幅很长，其实每行都在说明同一件事。逐行分析：

  • /usr/bin/ld:——报错的是链接器，不是编译器。 看出来这一点很重要：报错是 undefined reference， 说明你的语法一个字都没错，不要再去修改代码。
  • undefined reference to `readScores(int)'—— 它要找的符号，名字和参数都写在引号里了。
  • main.cpp:(.text+0x29)——谁在找。 这一行说的是「main.cpp 编译出来的代码里，有一处需要使用这个函数」。 0x29 是那段代码里的位置，你不用管它，每台机器都不一样。
  • in function `main'——精确到是哪个函数需要它。 文件大了，这一句可以节省一半排查时间。

所以这份报错翻译后的意思是： 

main.cpp 编译得到的目标文件，要用 readScores 和 printReport；
但我检查了你提供的全部文件，没有一份包含这两个函数。——链接器

它甚至告诉了你缺的是哪两个。缺少哪个函数，就补充哪个函数的定义。

报错里的内部名称

再查看它要找的那个符号，是否有些特殊： 

printReport(std::vector<int, std::allocator<int> >&)

你在代码里写的是 printReport(scores)， 它在说的是同一个函数。括号里那一长组内容，是 std::vector<int> 的完整写法——vector 其实有两个参数， 第二个是「用哪个分配器管理内存」，平时不用写，库为它指定了默认值 std::allocator<int>。

链接器不使用简称：函数的名字在底层是由名字 + 每个参数的类型拼出来的 （所以同名不同参数的两个函数才能共存）。 它报的时候用的是全名，能够认出对应哪一行代码即可。

看到这一长组内容时，不必紧张

记住三件事即可：它说 undefined reference → 是「没有」不是「写错」； 引号里是它要的符号；前面那个文件名是「谁在要」。

练习

练习 1-8

不用两个文件，一个文件也能报出一模一样的错—— 声明了，但从来没兑现： 

#include <iostream>

int twice(int x);

int main() {
    std::cout << twice(21) << std::endl;
    return 0;
}

编译出来，查看报错。和课里那条比较一下，除了名字不一样，别的是不是都一样。

然后回答：-c 那一步为什么没有任何报错？ （提示：编译一个文件的时候，它只知道「有承诺」， 兑现是下一步的事。）

看答案

程序就是练习里的那一份，一个字符都没有改动：

#include <iostream>

int twice(int x);

int main() {
    std::cout << twice(21) << std::endl;
    return 0;
}

分两步编译（和 1.5 那个目录的 构建.txt 一样）：

g++ -Wall -c 1-8-err.cpp -o 1-8-err.o
g++ 1-8-err.o -o report

第一条没有任何报错就通过了，第二条：

/usr/bin/ld: 1-8-err.o: in function `main':
1-8-err.cpp:(.text+0xe): undefined reference to `twice(int)'
collect2: error: ld returned 1 exit status

和课里 1.5 那条比一下：除了文件名和 0xe 那个数， 一个字符都不差。它需要的仍然是 twice(int)， 仍然是在 main 中需要的。

「-c 那一步为什么没有任何报错」：编译一个文件的时候， 编译器只管一件事——这个文件里的语法对不对。它读取到声明 int twice(int x);，就记录下「存在这个函数」， main 里调用它也就不算错。至于这个函数到底在哪里、 是否有人编写，是链接器下一步的事，编译这一步完全不检查。

这也解释了为什么看见 undefined reference 不要回头修改语法：它不是「你写错了」，是「它没找到」。

练习 1-9

把它补充完整，输出 42——两种补充方式都可以，任选一种：

  1. 把函数写在 main 上面（基础课的老办法）；
  2. 保持声明在上面，函数体写在 main 下面（1.3 的新办法）。
42

补完之后，如果你用的是第二种补法，把上面那个 int twice(int x); 那一行删除后尝试——编译一下，查看报错变成了哪一条。 （第一种补法没有这一行，也就没有这一步。） 同一条道理：该有的符号没有——只是这次报错的是编译器，不是链接器。

看答案

第二种补法——声明留在上面，函数体写在下面：

#include <iostream>

int twice(int x);

int main() {
    std::cout << twice(21) << std::endl;
    return 0;
}

int twice(int x) {
    return x * 2;
}

42。

第一种补法（把整个函数移到 main 上面）当然也可以， 那是基础课的原有办法。两种的区别只有一条： 编译器读到 main 的时候，是否已经读取到这个名称。

至于「把声明那行删掉」：删了它、函数体又留在下面，就无法编译了， 报的是 error: ‘twice’ was not declared in this scope， 位置正好指在 main 里那句 twice(21) 上。 编译器自上往下读，读到这里还没有读取到任何名为 twice 的声明， 只能报告「这个名称尚未声明」。

不要和上一题那条混淆：上一题是链接期「有声明，但没有定义」， 这一条是编译期「根本没有声明」。判断错误的人（ld 还是 g++）、字面、发生的时间，都不一样—— 查看报错是谁输出的，就知道该往哪里查找。

你现在能写什么：你能把 undefined reference 理解为通俗说明， 知道它在说明「谁需要、需要什么」，也知道这时候该回头看的不是语法。 这一部分到这里就完整了：一个程序拆成几个文件， 每个文件里放什么、怎么编译、出错后从哪里查找。 下一部分让构建工具替你记录这些命令。
