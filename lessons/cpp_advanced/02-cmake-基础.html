第 2 部分

cmake 基础

第 1 部分最后，你那个工程是用三条手动输入的 g++ 命令编译的。 这一部分把这串命令交出去：先交给 make，再交给 cmake。 五课下来，你能自己写一份 CMakeLists.txt， 也能读懂一份一百多行的——那种真在跑的工程里的cmake。

2.1手动输入 g++ 到头了

1.4 那一课，你把一条命令拆成了三条： 

g++ -Wall -c main.cpp -o main.o
g++ -Wall -c stats.cpp -o stats.o
g++ main.o stats.o -o report

三个文件，三条命令，还行。这一课先说清楚「再多几个会怎么样」， 然后把这件事交给两个工具。它们的分工只有一句话， 但这句话是这一部分的地基，先摆在这儿：

make 按配方执行，cmake 写配方

make 是那个真正执行构建的：你给它一份配方， 它照着一步步执行命令，还知道哪几步不用重来。 cmake 不执行构建，它是替你写那份配方的—— 你只告诉它「我这个工程是什么样的」，配方它自己生成。

三条命令，文件一多就不够用

三个文件三条命令。三十个文件呢？三十条。 真正麻烦的还不是「打得多」，是每改一次都得重来一遍， 而且你得记住哪几个文件跟着变了。

比如你只改了 stats.cpp 里的一行——main.cpp 一个字没动， 为什么重新编译它？可手动输入的人往往不区分这件事，常常把三条命令全部执行一遍， 然后在旁边等。

让机器记这件事。它的办法是：把「谁靠谁」和「怎么做」写成一份文件， 摆在工程里。这份文件叫 Makefile。

把配方写下来：一份 Makefile

就是 1.4 那三条命令，写成配方长这样： 

report: main.o stats.o
	g++ main.o stats.o -o report

main.o: main.cpp stats.h
	g++ -Wall -c main.cpp -o main.o

stats.o: stats.cpp stats.h
	g++ -Wall -c stats.cpp -o stats.o

clean:
	rm -f *.o report

一行一行读。冒号左边是要生成的文件，右边是生成它依赖的文件：

  • report 靠 main.o 和 stats.o；
  • main.o 靠 main.cpp 和 stats.h；
  • stats.o 靠 stats.cpp 和 stats.h。

冒号下面那一行缩进的，是做法——原样交给 shell 执行， 就是 1.4 里你手动输入的那几条，一个字都没有变。

最后那个 clean 是另一回事：它不产出任何文件， 就是把产物删掉重来。这类「假目标」是约定俗成的，名字叫 clean （rm 就是 remove）。

有了这份文件，编译就变成一句话： 

make
g++ -Wall -c main.cpp -o main.o
g++ -Wall -c stats.cpp -o stats.o
g++ main.o stats.o -o report

注意它把每条命令都打在屏幕上了。make 不藏着掖着—— 你随时看得见它到底编了哪几个文件、跳过了哪几个。 这一点从今往后都有用：出了问题，先看它这一步做了什么。

它省在哪儿

什么都不改，再来一次： 

make
make: “report”已是最新。

一条命令都没跑。现在改一处：把 stats.cpp 里打平均分那行的 %4.1f 改成 %5.2f（多留一位小数），保存，再 make： 

make
g++ -Wall -c stats.cpp -o stats.o
g++ main.o stats.o -o report

只有两条。main.cpp 一个字没动，make 就没碰它。

它凭什么知道？看时间。stats.o 比 stats.cpp 老， 那就是「源文件改过了，重做」；main.o 比 main.cpp 新， 那就跳过。整件事就这么朴素——make 不认识 C++， 它只看文件名和修改时间。

那它怎么知道改了 stats.h 要重编谁？靠 Makefile 里写的那两行。 把 stats.h 的时间戳更新一下（一个字符都不用改），再 make： 

make
g++ -Wall -c main.cpp -o main.o
g++ -Wall -c stats.cpp -o stats.o
g++ main.o stats.o -o report

两个都重编了。因为 main.o 和 stats.o 的依赖里 都写着 stats.h——就是这两行： 

main.o: main.cpp stats.h
stats.o: stats.cpp stats.h

这两行里那个 stats.h 不是装饰，是 make 唯一的依据。 漏写一个头文件，改了它 make 也不会重新编—— 编译生成的文件和源码不一致，而它不会有任何提示。 这是 Makefile 最常见的坏法，比报错难查得多。

Tab 和空格：当场跑一次

Makefile 有一个著名的易错点，值得当场运行一次： 做法那一行开头必须是一个 Tab，四个空格不行。

把上面第一段做法开头的 Tab 换成四个空格，别的都不动，然后 make： 

Makefile:2: *** 缺失分隔符。 停止。

「缺失分隔符」说的就是「这一行我看不出是做法」。

为什么这个易错点如此有名？因为它不可见。在编辑器里， 一个 Tab 和四个空格看上去几乎一样，目录里也看不出来。 更麻烦的是有些编辑器会自动把 Tab 转成空格—— 看起来是在帮你排版。

真遇到了怎么办

上面那句报错里带着 Makefile:2，行号是准的。 照着行号找到那一行，把行首那几个空格删掉、按一下 Tab 键。 Makefile 里凡是缩进的地方都是 Tab，从头到尾一个空格都不要用。

可它也是手写的

Makefile 省掉的是「记不住」，可它自己还是人写的。 文件一多，这份「谁依赖谁」的清单也要一行一行写—— 第 2.5 课那份真实工程，三十个源文件，就需要三十来行。

而且它认地方：这份文件是写给 Linux 上那个 make 看的。 换一套工具链，规则、写法、连命令的名字都不一样。

那，配方能不能也自动生成？能。这就是 cmake 干的事。

给 cmake 的不是配方，是一句「我这个工程是什么样的」。 比如四行： 

cmake_minimum_required(VERSION 3.16)
project(demo LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 17)
add_executable(demo main.cpp)

运行一遍 cmake 之后，build/ 里生成一份 181 行的 Makefile——上面那些规则、依赖、Tab，全是它生成的。 那份文件的开头两行是它自己写的： 

# CMAKE generated file: DO NOT EDIT!
# Generated by "Unix Makefiles" Generator, CMake Version 4.1

「这个文件是 cmake 生成的，别改」——它的原话。 从今往后，配方那一层不归你管了。 你要维护的只有那四行：工程叫什么、用哪个标准、要编哪个程序。

剩下五课就是把这四行认全，再多认十几条常用命令。

练习

这一课两道题都需要实际操作。第一道要的是实际体验。

练习 2-1

把这一课那份工程自己输入一遍。五个文件： Makefile（上面那份，一个字别改，做法行用 Tab）、 main.cpp、stats.cpp、stats.h （就是 1.4 那三份），再建一个输入文件 main.in， 里面是那十个分数，一行，用空格隔开。

main.in 里是这一行十个分数： 

92 85 77 60 58 100 73 88 95 64

然后按这个顺序执行一遍，每一步都看一眼屏幕：
① make　② 什么都不改，再 make ③ make clean　④ 再 make　⑤ ./report < main.in

第 ② 步该是一句话，不是三条命令——那是这一课最值钱的地方。 

分数      92  85  77  60  58 100  73  88  95  64
总分     792
平均    79.2

最低      58
优         3

看答案

五个文件，和 1.4 那三份是同一份内容，多出来的两项是 Makefile 和 main.in。 

report: main.o stats.o
	g++ main.o stats.o -o report

main.o: main.cpp stats.h
	g++ -Wall -c main.cpp -o main.o

stats.o: stats.cpp stats.h
	g++ -Wall -c stats.cpp -o stats.o

	rm -f *.o report

做法那几行开头是一个 Tab，不是四个空格。 页面上看不出来——你复制过去之后，要自己确认一下： 把光标移动到 g++ 前面，按一下退格键， 该是一下退掉整个 Tab，而不是退掉一个空格。

五步执行完，屏幕上是这些（make clean 那一步没有输出， 是正常的——rm 删除后不输出任何内容）：

① make：三条命令全部执行一遍；

② 再 make：只输出一句 make: “report”已是最新。 这一步是这道题的正题。一个文件都没有编译， 因为它检查时间戳，发现所有文件都比自己的产物旧；

③ make clean：把 *.o 和 report 删掉，没有输出；

④ 再 make：又三条——上一步把产物删除了， 它必须从头执行；

⑤ ./report < main.in：输出那张表。

如果第 ② 步输出的仍然是三条命令，多半是 make 没有找到那份 Makefile（比如你在上一级目录里输入的）， 它就认为「没有需要执行的操作」了。

练习 2-2

拿你刚建好的那份 Makefile，把 report 那条做法开头的 Tab 换成四个空格（只改这一行）。然后 make，看它说什么。

看清楚那句话里带着的行号——这就是以后查这个问题的线索。 改回来（删掉空格、按一下 Tab）再 make 一次，它应该照常运行。 

Makefile:2: *** 缺失分隔符。 停止。
看答案

就把 report 那条做法开头的 Tab 换成四个空格： 

report: main.o stats.o
    g++ main.o stats.o -o report

main.o: main.cpp stats.h
    g++ -Wall -c main.cpp -o main.o

stats.o: stats.cpp stats.h
    g++ -Wall -c stats.cpp -o stats.o

clean:
    rm -f *.o report

然后 make，它一条命令都不执行编译，直接输出： 

Makefile:2: *** 缺失分隔符。 停止。

Makefile:2 说的是这份 Makefile 的第 2 行—— 对照上面那份文件数一下：第 1 行是 report: main.o stats.o， 第 2 行就是那条做法。位置给得是准的。

「缺失分隔符」里的「分隔符」就是 make 为 Tab 指定的名称： 在它看来，冒号下面那一行必须以一个 Tab 开头， 那才表示「这是做法」。四个空格不是记号， 所以它读到这里，觉得第 1 行那句 report: main.o stats.o 后面没有做法，就停止了。

改回来之后（删掉那几个空格、按一下 Tab 键）， make 照常运行。

不要只靠肉眼观察。一个 Tab 和四个空格在屏幕上看上去几乎一样， 在有些编辑器里还会显示成同样宽。确实无法确定的时候， cat -A Makefile 能把 Tab 显示为 ^I， 空格仍然显示为空格——可以直接区分。

你现在能写什么：一份手写的 Makefile， 以及看懂 make 每次打出来的那几行——它编了谁、跳过了谁、为什么。 下一课不再手写配方：只写四行，让 cmake 把配方生成出来。

2.2第一份 CMakeLists.txt

先说清楚名字。你要写的这份文件叫 CMakeLists.txt， 一个字母都不能改，尤其别漏了最后那个 s。 它摆在工程的根目录，和你的 .cpp 放在一起。

四行，一行一行读

就这四行： 

cmake_minimum_required(VERSION 3.16)
project(demo LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 17)
add_executable(demo main.cpp)

第一行，cmake_minimum_required(VERSION 3.16)。 这句话是对 cmake 说的：「我这份文件是按 3.16 那个版本的规矩写的， 你别拿比它更老的版本来跑。」

它不是「要求你的 cmake 至少是 3.16」——本机装的是 4.1.2， 比 3.16 新，仍然运行正常。 它的意思是版本低了要拦住，因为老版本可能不认你写的某些写法。 最低写多少，取决于你用了多新的写法：这四行里最简单的写法， 写 3.10 也能跑。

这个数字还有一个用处，「第一行那串数字不能乱写」那一节会讲—— 它是一个会当场报错的位置。先记住它长这样。

第二行，project(demo LANGUAGES CXX)。 给这个工程起个名字，顺便说清楚它用什么语言。

demo 是工程名。让它和你的可执行文件同名最简洁， 不过它俩其实不是一回事——名字只是个标签， 真正决定「编出什么」的是第四行。

LANGUAGES CXX 说的是「这个工程用 C++」 （CXX 就是 C++ 的写法，两个 X 是早年 C++ 编译器叫 c++ 留下的习惯）。 不写这一句，cmake 会默认去试 C 和 C++ 两套，配置的时候多花几秒。 写上，它就只找 C++ 那套。

第三行，set(CMAKE_CXX_STANDARD 17)。 set 是「定义一个名字并保存值」。这儿保存的是一个 cmake 本来就认的名字：CMAKE_CXX_STANDARD， 意思是「C++ 用哪一版的标准」。

为什么是 17 不是 11？因为你要用的特性里， auto、nullptr、范围 for 是 11 的， 结构化绑定、if 里带初始化是 17 的。 写 17，这些都能用。

第四行，add_executable(demo main.cpp)。 这一行才是真正执行构建的：编一个可执行文件，叫 demo， 拿 main.cpp 编。

四行各自管什么

第一行管「规矩」，第二行管「这是个什么工程」， 第三行管「用哪版语言」，第四行管「编出什么」。 前三行是铺垫，第四行是活。 一份 CMakeLists.txt 里可以有好几个 add_executable ——那就是「这个工程要编出好几个程序」。

build 目录，和那三条命令

现在把它跑起来。规矩是在工程里另建一个目录，在那里跑： 

mkdir -p build
cd build
cmake ..

一条一条看。

mkdir -p build 建一个叫 build 的目录 （-p 是「已经有了就别说」）。

cd build 走进去。

cmake .. 跑 cmake，后面那个 .. 是上一级目录—— 也就是告诉它「CMakeLists.txt 在上一级目录， 生成的文件放在我当前所在的目录」。

跑出来是这样： 

-- The CXX compiler identification is GNU 13.3.0
-- Detecting CXX compiler ABI info
-- Detecting CXX compiler ABI info - done
-- Check for working CXX compiler: /usr/bin/c++ - skipped
-- Detecting CXX compile features
-- Detecting CXX compile features - done
-- Configuring done (0.2s)
-- Generating done (0.0s)
-- Build files have been written to: build

前面六行是它在找编译器：找着了（/usr/bin/c++）、 试了一下、记录下来了。这几行只有第一次配置的时候会输出， 以后再运行就不会这么详细。

中间那两句 Configuring done / Generating done 说明它的任务完成了：配置完了，生成完了。

最后一句 Build files have been written to: build 是「配方写好了，摆在 build 里」。你那儿打出来的会是完整路径 （/home/你的名字/…/build 这样）， 这一页上为省地方写成了简写——后面凡是带路径的行都是这个道理， 你照着看一眼就知道是哪一条。

注意它到这里就停止了。它一个 .cpp 都没有编译。 cmake 的工作到「写好构建规则」为止，编译不由它负责。

看看它写了什么： 

ls
CMakeCache.txt
CMakeFiles
cmake_install.cmake
Makefile

四个文件。那个 Makefile 就是 2.1 里你手动写了很久的构建规则—— 你没有写，是它生成的。

CMakeCache.txt 是个备忘录：上一回找到的编译器、 你给的设置，都记在里面，下回直接用。 CMakeFiles/ 是一个目录：中间产物、每个目标各自的规则， 都存放在那里。cmake_install.cmake 负责「安装到其他目录」， 2.4 讲 install 的时候用到它。

接下来照 2.1 的老规矩来： 

make
[ 50%] Building CXX object CMakeFiles/demo.dir/main.cpp.o
[100%] Linking CXX executable demo
[100%] Built target demo

和 2.1 里那份手写的 Makefile 输出的内容很像——本来就是同一类。

然后跑： 

./demo
这份程序是 cmake 编译得到的。
四行 CMakeLists.txt，替换了手动输入的那串参数。
build 里的文件不要提交

build/ 整个目录都是生成物：几百个文件、夹着机器上 的绝对路径、换台机器就得重来一遍。它不该进版本库 （1.4 讲过的「中间文件不提交」那条，到这儿是同一个道理， 只是这次的中间文件有一堆）。

真要清理，最直接的一条是 rm -rf build，然后再建再配。 cmake 跑得快，配置一遍几秒钟，不用担心。

那串参数去哪儿了

1.4 里你手动输入的是这串： 

g++ -Wall -std=c++17 -c main.cpp -o main.o

那个 -Wall、那个 -std=c++17， 到 cmake 里写成什么了？第三行那个 set 管的正是后者。 看一眼它到底传了什么参数： 

cat CMakeFiles/demo.dir/flags.make

这个文件里记着这个目标编译时用的每一段参数。其中三行是关键： 

CXX_DEFINES =
CXX_INCLUDES =
CXX_FLAGS = -std=gnu++17

CXX_FLAGS 那行就是「传给编译器的参数」： set(CMAKE_CXX_STANDARD 17) 变成了 -std=gnu++17。

注意是 gnu++17，不是 c++17。 这不是打错了，是 cmake 故意的：它默认允许编译器那些 「标准之外、GNU 加的」扩展。想要严格的标准，得多写一句 关掉扩展： 

set(CMAKE_CXX_EXTENSIONS OFF)

平时两种写法没差别，读到别人的 CMakeLists.txt 里写着 gnu++17 的时候， 知道有这一回事就行。

CXX_DEFINES 和 CXX_INCLUDES 这两行是空的， 因为你还没要宏、没说头文件去哪儿找——那是 2.3 和 2.4 的事。 它们空着，但位置保留：以后写入的内容都放在这两行里。

还想看得更细，让 make 把每条命令原样打出来： 

make VERBOSE=1

在那一大堆输出里，真正编 main.cpp 的是这么一条： 

/usr/bin/c++   -std=gnu++17 -MD -MT CMakeFiles/demo.dir/main.cpp.o -MF … -o … -c main.cpp

先说那两个 …：这一行在你机器上是连着的 149 个字符。 -MF 和 -o 后面各跟着一串目标文件的路径—— 还是 CMakeFiles/demo.dir/main.cpp.o 这个名字， 一个带 .d 一个不带，页面上排不下，拿 … 省了； 其余字符一个都没有改动。这一行不用背也不用复制，看它包含什么即可。

中间那几个 -MD、-MF、-MT 是在生成一份「谁靠谁」的清单——就是 2.1 里你手写在 Makefile 里、 还怕写漏的那几行。cmake 让编译器自己把这份清单吐出来， 所以它不会漏：你 #include 了什么，它就知道要盯什么。 这一条比你手写强，强在这儿。

-Wall 不在上面——第四行没让它加。 想在 cmake 里加编译参数，用的是 2.4 那条 add_compile_options。

第一行那串数字不能乱写

第一行那个数字不是随便填的，写错了它当场拦你。 把 3.16 改成 3.0 试试： 

cmake_minimum_required(VERSION 3.0)
CMake Error at CMakeLists.txt:1 (cmake_minimum_required):
  Compatibility with CMake < 3.5 has been removed from CMake.

  Update the VERSION argument <min> value.  Or, use the <min>...<max> syntax
  to tell CMake that the project requires at least <min> but has been updated
  to work with policies introduced by <max> or earlier.

  Or, add -DCMAKE_POLICY_VERSION_MINIMUM=3.5 to try configuring anyway.


-- Configuring incomplete, errors occurred!

读这份报错的方法，和读编译器的报错一模一样。 第一行给位置：CMakeLists.txt:1， 第 1 行，出在 cmake_minimum_required 这一句上。 底下缩进的几段是它给你说的话。

Compatibility with CMake < 3.5 has been removed from CMake ——「和 3.5 以前的那些兼容性，已经从 cmake 里拿掉了」。 说白一点：你写的 3.0 太老了，这个 cmake 不认了。

为什么会这样？cmake 有个「规矩」（它叫 policy）： 一份老文件照着老规矩跑，一份新文件照着新规矩跑。 为了让新规矩能推进，它得有个截止线—— 新版 cmake 把「3.5 以前」这一档整个删了。 所以你写 3.0，它就当你是在说「我这文件是远古时候写的」， 直接拒绝。

下面还给了一条路：-DCMAKE_POLICY_VERSION_MINIMUM=3.5。 看见这条不要急着采用——它的意思是「我知道它版本老，仍然运行」。 真拿到一份写着老版本号的旧工程，正确动作是把那个数字改大， 而不是加参数硬压。加参数是留给「改不动那份文件」的时候的。

还有一个地方容易混：这个数字不是「你的 cmake 版本」。 本机是 4.1.2，你写 3.16、3.20、3.28 都能跑。 写小了才拦你。

去哪查本机是哪个版本

cmake --version。头一行就是版本号。 第 0 部分让你逐个 --version 的那一轮里就有它。

拆成三截读。

标准设错了

第三行 set(CMAKE_CXX_STANDARD 17) 设错了会怎样？ 把它改成 98——那是 C++ 最早那一版， 连 nullptr 都还没有：

这一条报错值得单独讲，因为它看上去不像版本问题。 同样一句「没声明过」，你要是把变量名打错了（nuulptr）， 报错看上去一模一样。区别在哪？

报错里那个类似 ↘ 的符号

main.cpp: In function ‘int main()’: 这一行是说 「下面的话都是说 main 这个函数的」。 它有时候会和第一条错印在同一行，看上去长； 这一份是分行印的。

target 的名字只能是 ASCII

最后一件事。你 1.4 那个可执行文件现在叫 report， 迁移过来直接就能用。可要是一不留神写成中文——例如： 

add_executable(报表 main.cpp)

这么写，cmake 也是当场拦你——注意，它停在第 4 行， 配置这一步就停了，一个源文件都没碰： 

CMake Error at CMakeLists.txt:4 (add_executable):
  The target name "报表" is reserved or not valid for certain CMake
  features, such as generator expressions, and may result in undefined
  behavior.

The target name "报表" is reserved or not valid—— 「这个名字被保留了，或者不合法」。

为什么不行？因为 target 的名字不只是个名字： cmake 会拿它去拼文件名（报表.o、报表）、 拼目录名、拼一串别的工具的输入。 这些地方对「什么能用什么不能用」有硬规定， cmake 直接把允许的字符收在一个安全范围里： 字母、数字，加上 . - _ +， 别的都不行。

那中文就白学了？不是——看清楚了，它拦的是 target 名。 换成工程名、换成字符串，中文都能待： 

project(统计表 LANGUAGES CXX)
add_executable(report main.cpp stats.cpp)

工程名叫 统计表（中文，可以）， target 叫 report（ASCII，必须）， 而程序跑起来照旧打中文——那跟 cmake 没关系了。

cmake 这一点上还有一个更细微的易错点：它能阻止中文 target 名， 可它拦不住中文变量名——那个报出来的错比这一条难懂得多。 2.4 最后一节拿它当场跑一次。

2.4常用的那十几条命令

到这儿你已经会写四行，还会加头文件目录了。 剩下的常用命令还有十来条——这一课把它们摆成一张「命令桌」， 一条一条实际运行一遍。运行完你就有了自己的一份模板， 以后开新工程照着改。

先把桌子的样子摆出来。这是一份 CMakeLists.txt， 编号是这一课的讲法，不是 cmake 的规矩： 

cmake_minimum_required(VERSION 3.16)

# ① project：工程名、版本号、用什么语言。版本号后面的 configure_file 要用
project(命令桌 VERSION 1.2.0 LANGUAGES CXX)

# ② set：定义一个名字并保存值，使用时写 ${名字}
set(DESC_TEXT "命令桌")

# ③ message：打印一句。STATUS 是「正常信息」那一档
message(STATUS "开始配置：${DESC_TEXT}")

# ④ option + if：一个开关，第二个位置是默认值
option(EXTRA_LINE "打开的话程序多打一行" ON)
if(EXTRA_LINE)
  message(STATUS "要多打一行：开")
else()
  message(STATUS "要多打一行：关")
endif()

# ⑤ find_package：在本机查找「多线程库的位置」
find_package(Threads REQUIRED)
message(STATUS "线程找着了：${Threads_FOUND}")
message(STATUS "还要额外链的线程库：${CMAKE_THREAD_LIBS_INIT}")

# ⑥ add_subdirectory：把子目录那份 CMakeLists.txt 也拉进来一起配
add_subdirectory(工具库)

# ⑦ configure_file：拿一个模板生成一个头文件，@变量@ 会被换掉
configure_file(include/version.h.in ${CMAKE_CURRENT_BINARY_DIR}/生成/version.h @ONLY)

# ⑧ add_compile_options：给这个目录底下所有编译命令都加一段参数
add_compile_options(-Wall)

# ⑨ add_executable 加两个 target_*：这才是「要编什么、去哪儿找头文件、链谁」
add_executable(desk main.cpp)
target_include_directories(desk PRIVATE ${CMAKE_CURRENT_BINARY_DIR}/生成)
target_link_libraries(desk PRIVATE tools Threads::Threads)

# ⑩ install：说明「安装到其他目录」时复制哪些文件
install(TARGETS desk DESTINATION bin)
install(FILES ${CMAKE_CURRENT_BINARY_DIR}/生成/version.h DESTINATION include)

一共二十来行，十件事。一条一条来。

一张命令桌

先说清楚这份工程比 2.3 多出来的两个文件，否则下面几条讲不通。

一样是子目录。 工具库/ 里有一对 util.h / util.cpp，还有它自己的一份 CMakeLists.txt： 

add_library(tools STATIC util.cpp)

target_include_directories(tools PUBLIC .)

三行里只有两行有用：add_library 建一个库 （STATIC 是「静态库」，就是 1.4 里那些 .o 打成一个包，叫 libtools.a）， PUBLIC 让「用这个库的人也能找到它的头文件」。

另一样是模板文件。 include/version.h.in 不是头文件， 是一张等着被填的表格： 

#define VERSION_TEXT "@PROJECT_VERSION@"
#define DESC_TEXT "@DESC_TEXT@"

#cmakedefine EXTRA_LINE

那些 @…@ 是占位符，配置的时候会被填充。 填充后得到的内容（后面 ⑦ 要讲）才是一份真正的头文件， 摆在 build/ 里——不是源码目录， 所以 ⑨ 里还得专门告诉编译器去哪儿找它。

这份工程一共六份文件，摆开是这样（两份 CMakeLists.txt 和那份模板都贴在旁边了）： 

命令桌/
├── CMakeLists.txt
├── main.cpp
├── include/
│   └── version.h.in
└── 工具库/
    ├── CMakeLists.txt
    ├── util.h
    └── util.cpp

剩下三份是普通程序，新建一个目录，照着输入： 

// 工具库/util.h
#ifndef TOOLS_H
#define TOOLS_H

int 双倍(int x);

#endif
// 工具库/util.cpp
#include "util.h"

int 双倍(int x) {
    return x * 2;
}
// main.cpp
#include <iostream>

#include "version.h"
#include "util.h"

int main() {
    std::cout << "版本 " << VERSION_TEXT << " —— " << DESC_TEXT << std::endl;
    std::cout << "工具库说：双倍(21) = " << 双倍(21) << std::endl;
#ifdef EXTRA_LINE
    std::cout << "这一行是那个开关打开的。" << std::endl;
#endif
    return 0;
}

三份里最值得看的是 main.cpp：它 #include 的两份 头文件都不在源码目录里——version.h 是 ⑦ 生成到 build/ 里去的，util.h 在子目录 工具库/ 里。两份都得靠 CMakeLists.txt 里那两行指路， 编译器才找得着，这正是 ⑨ 那两句在干的事。

①–④ 名字、变量、打印、开关

① project(命令桌 VERSION 1.2.0 LANGUAGES CXX)

比 2.2 那份多了 VERSION 1.2.0——给工程编个版本号。 这个数字不是摆设：project 会顺便把它存进几个变量里， 最常用的是 PROJECT_VERSION（值是 1.2.0）。⑦ 的模板里那个 @PROJECT_VERSION@ 填的就是它—— 程序里打出来的「版本 1.2.0」是这么来的。

工程名还是中文，照旧没问题。

② set(DESC_TEXT "命令桌")

set 是「定义一个名字并保存值」。 DESC_TEXT 是你自己定义的名字（2.2 里 CMAKE_CXX_STANDARD 是 cmake 本来就认的名字， 这一条是你自己定义的）。 取的时候写 ${DESC_TEXT}——${} 是「把里面的名字 换成它的值」。注意引号：值里有空格、有中文， 一律拿引号包起来，不然它会把空格当分隔符切开。

③ message(STATUS "开始配置：${DESC_TEXT}")

往屏幕上打一句。配置的时候打出来的是： 

-- 开始配置：命令桌

前面那个 -- 是 STATUS 加上的， 不用自己写。这就是「在 cmake 里打印」的办法， 往后调试配置脚本全靠它——**报错之前先把它打出来看看**。

④ option 加 if 

option(EXTRA_LINE "打开的话程序多打一行" ON)
if(EXTRA_LINE)
  message(STATUS "要多打一行：开")
else()
  message(STATUS "要多打一行：关")
endif()

option 是一个开关。 三个位置：名字、一句给人看的说明、默认值。 默认值决定它开还是关。

if / else / endif 是 cmake 自己的条件语句。写法上有个和 C++ 不一样的地方值得留意： cmake 里判断一个开关，直接写名字，不写 ${}。 写成 if(${EXTRA_LINE}) 在某些情况下会读成 if(ON)、某些情况下读成 if()——那就不对了。 判断条件写名字，取值才写 ${}。

开的时候屏幕上是这一句（上面那份真实输出里的第二句）： 

-- 要多打一行：开

option 真正的用处不在 if，在于它可以在命令行上改： 

cmake .. -DEXTRA_LINE=OFF

-D 是「把哪个名字定成什么值」。 这个开关还会往下传进程序里：⑦ 的模板里那行 #cmakedefine EXTRA_LINE，开的时候生成 #define EXTRA_LINE，关的时候变成一句注释—— main.cpp 里 #ifdef 就判得出来。 配置时的开关和程序里的宏，就是这么连起来的。 练习 2-8 就要你关一次看看。

⑤–⑥ 找库、拉子目录

⑤ find_package(Threads REQUIRED)

「在本机查找多线程库的位置」。 REQUIRED 是「找不到就直接报错停下」， 不写的话它只是找不到，后面链接的时候才会报错—— 那时候的报错难懂得多。凡是你确定要用的，都写上 REQUIRED。

它做的事是把结果填进几个变量里，然后你就可以 message 出来看： 

message(STATUS "线程找着了：${Threads_FOUND}")
message(STATUS "还要额外链的线程库：${CMAKE_THREAD_LIBS_INIT}")
-- 线程找着了：TRUE
-- 还要额外链的线程库：

第一句是 TRUE，找着了。

第二句是空的——这一句值得停一下。早年用多线程， 编译和链接都得显式加上 -pthread，那个变量里就是这个。 现在的 C 库已经把线程相关功能并入，不需要额外链接任何内容， 所以变量是空的。

空的不是错。真要在别处（比如一份老一点的文档）看见 CMAKE_THREAD_LIBS_INIT，知道它为什么可能是空的就行。

find_package 找到的库怎么使用？过一会儿 ⑨ 的 target_link_libraries 里会写 Threads::Threads—— 带两个冒号的那种写法，就是 find_package 交给你的「结账方式」。

屏幕上前头还有两行： 

-- Performing Test CMAKE_HAVE_LIBC_PTHREAD
-- Performing Test CMAKE_HAVE_LIBC_PTHREAD - Success

这就是上面那句「C 库已经把线程并进去了」—— find_package(Threads) 不是去翻目录找文件， 而是真的编一个小程序试一下，试出来能跑， 才下结论。所以它多花一点时间，也所以它准。

⑥ add_subdirectory(工具库)

「工具库/ 那个目录里也有一份 CMakeLists.txt，一并读进来」。 子目录那份里建了个库 tools， 建完之后上层就能用了——⑨ 里的 target_link_libraries(desk PRIVATE tools …) 链的就是它。

工程分成几个目录、每个目录一份 CMakeLists.txt，是常规做法。 这一课只有一层，第 2.5 课那份真实工程也是这个路子， 只是目录更多。

⑦–⑧ 生成头文件、加参数

⑦ configure_file(include/version.h.in ${CMAKE_CURRENT_BINARY_DIR}/生成/version.h @ONLY)

拿模板生成一份真文件。三个位置：

  • 模板在哪儿：include/version.h.in；
  • 生成到哪儿：${CMAKE_CURRENT_BINARY_DIR}/生成/version.h；
  • @ONLY：只换 @…@ 那种写法。

CMAKE_CURRENT_BINARY_DIR 是「我现在这个目录， 对应的 build 里那一层」——在 build/ 里就是 build/ 自己。所以生成出来的是 build/生成/version.h。它不在源码目录里， 这就是 ⑨ 里还得专门加一行告诉编译器去哪儿找的原因。

生成出来的那份，正文长这样： 

#define VERSION_TEXT "1.2.0"
#define DESC_TEXT "命令桌"

#define EXTRA_LINE

对一对：@PROJECT_VERSION@ 变成了 1.2.0 （① 那个版本号），@DESC_TEXT@ 变成了 命令桌（② 那个变量）， #cmakedefine EXTRA_LINE 变成了 #define EXTRA_LINE（④ 那个开关的开状态）。

@ONLY 这个后缀先照着写。它的意思是「只识别 @…@， 不认 ${…}」——不写的话， 模板里凡是 ${} 形式的文本也会被替换， 而你那份头文件里可能正好有不该被换的。

⑧ add_compile_options(-Wall)

给编译命令加参数。-Wall 是 1.4 里你手动输入的那个—— 到这儿它终于有地方放了。

加没加上，不用猜，去 flags.make 里看： 

cat CMakeFiles/desk.dir/flags.make
CXX_FLAGS = -Wall

这一行现在有内容了。回头对照 2.2 那份： 那时它是 -std=gnu++17， 现在多了一个 -Wall。

这里有个会出错的细节。 子目录那个库的 flags.make 里，CXX_FLAGS 是空的： 

cat 工具库/CMakeFiles/tools.dir/flags.make
CXX_FLAGS =

同一份 CMakeLists.txt 里的 add_compile_options(-Wall)，为什么管不到子目录？

因为它写晚了。 ⑤ 那一行是「给从现在起这个目录底下 所有编译命令都加一段参数」，而 ⑥ 的 add_subdirectory 排在它前面—— 子目录在那一刻已经加入，这一行无法影响它。

这不是猜的：把 add_compile_options(-Wall) 那一行挪到 add_subdirectory 上面， 再删掉 build 重新配一遍，那个 flags.make 里的 CXX_FLAGS 就变成 -Wall 了。

记住这一条规则：cmake 是一行一行读下来的， 写在前面的管不到后面的，写在后面的也管不到前面的。 这条规律后面还会再遇到一次（⑩ 的 install 也是「谁在前谁生效」）。

⑨–⑩ 编译什么、安装到哪

⑨ 三行连着写 

add_executable(desk main.cpp)
target_include_directories(desk PRIVATE ${CMAKE_CURRENT_BINARY_DIR}/生成)
target_link_libraries(desk PRIVATE tools Threads::Threads)

这一组是三件事，都得有：

  • add_executable：要编什么。这个 2.2 就会了。
  • target_include_directories：头文件去哪儿找。 这儿指的是 ⑦ 生成的那个目录——不然 main.cpp 里的 #include "version.h" 找不到。
  • target_link_libraries：链谁。 tools 是 ⑥ 那个子目录建的库， Threads::Threads 是 ⑤ 找出来的。

这三个命令都以 target_ 开头，都以目标的名字 作为第一个参数。这个形式是 cmake 当前的规范写法： 每个目标自己管自己的事， 而不是在一个全局的地方一次说清所有目标的事—— 后者（像第 2.5 课里那片 include_directories(...)）是老写法， 一份文件里目标多了会互相串。你现在起手就照新的写。

再说 PRIVATE。2.3 里出现过一次，当时说「先照着写」， 现在可以说了：

PUBLIC 和 PRIVATE，一句话分工

target_link_libraries(desk PRIVATE tools) 的意思是 「我自己要用 tools，但用我 desk 的人 不需要知道这件事」。

子目录那份里写的是 target_include_directories(tools PUBLIC .)： 「用我这个库的人也得能找到我的头文件」—— 因为 main.cpp 里要 #include "util.h"， 而那个文件在 工具库/ 里。 写 PRIVATE 就找不到，编译当场报 「util.h: 没有那个文件或目录」。

记法：给自己用的写 PRIVATE，给用你的人也留一份的写 PUBLIC。

然后编译： 

make

[ 50%] Linking CXX static library libtools.a
[ 50%] Built target tools
[ 75%] Building CXX object CMakeFiles/desk.dir/main.cpp.o
[100%] Linking CXX executable desk

注意第一行和第三行：子目录那个库先编， libtools.a 打出来，然后才轮到 desk。 顺序不用你操心——⑨ 里说了 desk 链 tools，cmake 就知道谁在前。

跑起来： 

./desk

工具库说：双倍(21) = 42

三行，三个来路：版本号来自 ①，工具库来自 ⑥， 最后一行来自 ④ 那个开关（关掉它这行就没了）。

⑩ 两行 install 

install(TARGETS desk DESTINATION bin)
install(FILES ${CMAKE_CURRENT_BINARY_DIR}/生成/version.h DESTINATION include)

第一行说明「安装的时候把 desk 复制到 bin/」， 第二行说明「把生成的头文件复制到 include/」。

install 不是「现在就复制」——它只是登记， 说明「将来安装的时候，哪些文件复制到哪里」。 实际复制由另外一条命令完成： 

cmake --install . --prefix 安装目录
-- Install configuration: ""
-- Installing: build/安装目录/bin/desk
-- Installing: build/安装目录/include/version.h

--prefix 是「安装到哪个目录」。 两行 Installing 就是 ⑩ 登记的那两个文件。

为什么要分成「登记」和「实际安装」两步？因为安装到哪个目录、 什么时候安装，是使用的人的事，不是写工程的人的事。 你只负责说明「我这个工程有哪些文件需要安装」， 接手的人想安装到 /usr/local 还是安装到自己的主目录， 他自己定。

失败别慌

这个开关默认是开的。真要让程序少打一行， cmake .. -DEXTRA_LINE=OFF （记得先把 build 删了，或者就着现在的 build 重配一次也行——-D 是命令行给的， 优先级比文件里写的默认值高）。

中文能待在哪儿

这一课那份文件里，中文到处都是：工程名叫 命令桌、 变量是 DESC_TEXT（值才是中文）、 message 打的是中文、连打印出来的头文件里都是中文。 2.3 却说了「target 名字只能是 ASCII」。到底哪儿能、哪儿不能？

补一个 2.3 没跑的：变量名也不能用中文。 而且这个错比 target 名那个难懂得多。看： 

set(说明文字 "统计表（第 2 版）")
message(STATUS "这次建的是：${说明文字}")
CMake Error at CMakeLists.txt:6 (message):
  Syntax error in cmake code at

    CMakeLists.txt:6

  when parsing string

    这次建的是：${说明文字}

  Invalid character ('�') in a variable name: ''

一层一层读这份报错，它是这么给的：

  • CMakeLists.txt:6 (message)：出在第 6 行， 出在 message 这一句上；
  • Syntax error in cmake code at CMakeLists.txt:6： 第 6 行有个语法错；
  • when parsing string 这次建的是：${说明文字}： 在解析这个字符串的时候；
  • Invalid character ('�') in a variable name: ''： 在一个变量名里读到了非法字符。

最后那句才是真相：它是在 ${} 里面读变量名的时候 报出来的。 所以那个 '�' 不是乱码——它就是它读不出来的那个中文字， cmake 连原样吐回来都做不到。

还有一个后果值得注意。set(说明文字 "…") 那一句在第 5 行， 可报错说的是第 6 行。因为 cmake 读一行是一行： 第 5 行 set 的时候，说明文字 只是被当成 「一串字」存下来，它不检查这串字合法不合法； 到第 6 行真正要用 ${} 去查找这个名字了，才会报错。

所以报错指的位置是「用它」的地方，不是「写它」的地方。 这句话在别的地方也成立——真实工程里一份文件几百行， 报错指的那一行常常不是你刚写的那一行。

把这一课的中文规矩收成一张表：

  • 可以：工程名（project 的第一个位置）、 字符串的值、message 打的话、注释；
  • 不行：target 的名字、变量的名字——凡是 cmake 要拿去当名字用的，都得是 ASCII；
  • 还可以：源文件名（stats.cpp 一直是中文， 从头到尾没事）。

为什么 target 名和变量名要卡这么死？因为它们会流到 cmake 外面去：拼文件名、拼命令行参数、拼给别家工具看的输入。 字符串和注释只在 cmake 内部使用， 不会传出，也就没有人检查它是什么字符。

练习 2-7 就是把这个错改对：中文该留的留着， 不该留的换掉。

先说清楚这是哪一份

    * 34 include_directories(/opt/intel/oneapi/mkl/latest/include)、
    * 35 link_directories(/opt/intel/oneapi/mkl/latest/lib/intel64)、

它给了三个行号。三个都不对。

  • 说 CUDA_GEN_CODE 在第 20 行—— 打开文件一看，是第 27 行； 第 20 行是另一句 find_package；
  • 说 MKL 那两行在第 34、35 行—— 实际在第 62、63 行；
  • 说 libmkl_rt.so 在第 108 行—— 实际在第 137 行。第 108 行是源文件清单收尾的那个 )，跟 MKL 一点关系都没有。

不止行号。README 说那两行写的是 /opt/intel/oneapi/mkl/latest/include， 而文件里现在是 ${MKLROOT}/include—— 一个环境变量，连路径都不写了。 拿 README 里那串路径去文件里搜，一个字都搜不着。

为什么会这样，怎么办

因为代码在动，README 不动。 上面增加了一行 find_package， 底下所有内容就向下移动一行；这样移动了七八回， README 里那几个数字就全错位了。

这不是这份工程特有的毛病，是所有 写行号的文档都会遇到的事。

所以：README 说「第几行」的时候，别去数行，去搜名字。

用编辑器搜 CUDA_GEN_CODE， 它落在哪一行就是哪一行； 搜 libmkl_rt.so，同理。 名字比行号稳——名字是内容，行号只是个位置。

这就是练习 2-9 要你练的最后一件事。 改一处真文件，靠的是搜名字，不是数行。

还有一句要说清楚：上面那三个行号，是这份文件写这篇课文时的样子。 你自己手上那份工程，行号可能又变了。 这不是课文写错了——这正好是那一课的结论：行号靠不住。

cmake_minimum_required(VERSION 3.16)

project(统计表 VERSION 1.0.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
add_compile_options(-Wall)

# 安装到其他目录时复制哪些文件：可执行文件进 bin
install(TARGETS stats DESTINATION bin)

然后安装，再运行安装出来的那一份： 

cmake --install . --prefix 安装位置
./安装位置/bin/stats < ../main.in

注意最后运行的是 ./安装位置/bin/stats， 不是 ./stats。 这是这道题的正题：install 登记的内容 真的被复制过去了，而且复制过去那一份是可以运行的—— 它不依赖 build 里的任何内容。

安装那一步输出的 -- Installing: 后面， 路径应当从你为 --prefix 指定的内容开始。

install 那个 DESTINATION bin 是相对于 --prefix 的： bin 是「安装到前缀下的 bin 目录里」。 这就是为什么同一份工程，换个 --prefix 就能安装到其他位置——工程里一个字符都不需要修改。

另外记录一句：真正安装到系统里的时候， bin/ 那份程序必须能够直接输入名字运行， 所以 bin 这个目录名是约定俗成的， 不要改成其他名称。

你现在能写什么：一份二三十行的 CMakeLists.txt， 建库、拉子目录、找依赖、生成头文件、装到别处都行； 拿到一份一百七十多行的真文件，也能扫一遍就说出它在干什么、 该改的地方在哪儿。
