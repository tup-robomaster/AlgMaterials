常见文件

这一部分处理项目里最常见的几种文件：纯文本、JSON、YAML、Markdown、 Shell 脚本、模型文件与日志。要求是看懂：知道每种文件长什么样、 每一部分表示什么、出问题时先看哪里。例子仍然可以运行， 但不要求逐条输入；模型文件只要求了解格式与转换关系，不要求实际转换。

开始之前：练习目录还在吗

第一行会删除整个练习副本，路径不要改成自己的目录。 复制完成后，用 pwd 确认当前目录是 /tmp/other-basics/示例代码。

3.1文本与编码

文本文件在编辑器里显示为字符，在磁盘上保存为字节。字符与字节之间的对应规则 叫编码（encoding）。同一段中文，用 UTF-8 保存和用 GBK 保存，字节不同； 用错编码打开，就会看到乱码。这一课从字节看起，认清 file、 od、iconv 三个工具的输出。

文件里存的是字节

练习目录 3.1-文本与编码 里有几份内容相近的文本。 先看 utf8.txt 的前六个字节： 

cd /tmp/other-basics/示例代码/3.1-文本与编码
od -An -tx1 -N 6 utf8.txt
 e7 9b b8 e6 9c ba

od 是查看文件字节的工具，名字来自 octal dump（八进制转储）。 这里用了三个选项：-An 不显示每行开头的偏移地址， -tx1 把每个字节显示成两位十六进制数，-N 6 只读前六个字节。需要查看其他格式时，可以搜索「od 命令 十六进制」。

这六个字节对应两个汉字：「相」的 UTF-8 编码是 e7 9b b8， 「机」是 e6 9c ba。一个汉字在 UTF-8 里通常占三个字节。 英文字母在 ASCII 范围内只占一个字节，例如 c 是 63， a 是 61。编辑器把字节按编码翻译成字符显示； 文件本身没有「字符」，只有字节。

ASCII 与 UTF-8

目录里有五份文本，用 file 看它们的类型： 

file *.txt
ascii.txt: ASCII text
bom.txt:   Unicode text, UTF-8 (with BOM) text
crlf.txt:  Unicode text, UTF-8 text, with CRLF line terminators
gbk.txt:   ISO-8859 text
utf8.txt:  Unicode text, UTF-8 text

file 根据文件开头的字节判断类型，不看扩展名。 ascii.txt 只有英文字母、数字和空格，属于 ASCII； utf8.txt 含中文，是 UTF-8。输出里文件名后面补了空格对齐， 所以冒号不在同一列。

gbk.txt 显示为 ISO-8859 text，这不是说它真是 ISO-8859 编码。GBK 的字节范围与 ISO-8859 有重叠，file 只能确定它不是合法的 UTF-8，无法仅凭字节区分 GBK 和其他单字节编码。 要确认中文文件的编码，需要知道它的来源，或者用编辑器、转换工具试读。

ASCII 是最早的字符编码，只定义 0–127，包含英文字母、数字、标点和控制字符。 UTF-8 是 Unicode 的一种变长编码：ASCII 字符仍占一个字节，其他字符占两到四个字节。 GBK 是中文的旧编码，一个汉字通常占两个字节。新建文件应优先用 UTF-8； 只有在必须与旧程序交换数据时，才使用 GBK。

如果一份 UTF-8 文件被按 GBK 打开，中文会显示成乱码；反过来也一样。 字节没有损坏，只是翻译规则用错了。遇到乱码先确认文件本来的编码， 不要直接改内容。

BOM 与 CRLF

bom.txt 与 utf8.txt 的内容相同，字节数却多三个： 

wc -c bom.txt utf8.txt
30 bom.txt
27 utf8.txt
57 总计

wc -c 统计字节数。最后一行是合计，文字随终端语言变化： 中文环境是「总计」，英文环境是 total。多出来的三个字节在文件开头： 

od -An -tx1 -N 6 bom.txt
 ef bb bf e7 9b b8

ef bb bf 是 UTF-8 的字节顺序标记（Byte Order Mark，BOM）。 它对应 Unicode 字符 U+FEFF，放在文件开头表示「这是 UTF-8」。 有些 Windows 编辑器保存 UTF-8 时会自动加上 BOM。BOM 对文本编辑器通常无害， 但对编译器、Shell 脚本和某些配置解析器可能是多余内容：脚本第一行前多了三个字节， #! 就不在文件开头，执行时可能报错。写代码、脚本和配置文件时， 保存为「UTF-8 无 BOM」。

crlf.txt 的问题是换行符。Linux 与 macOS 用 LF（换行，字节 0a）表示一行结束；Windows 用 CRLF（回车加换行，字节 0d 0a）。file 的输出里写着 with CRLF line terminators，就是提醒这一点。CRLF 在普通文本里 通常只多一个字节，但在 Shell 脚本里会带来实际问题：解释器会把 \r 当成命令的一部分，出现 bad interpreter 或奇怪的参数。 跨平台传递脚本后，如果运行时报这类错误，先检查换行符。

这两种情况都可以在编辑器里转换：保存时选择「UTF-8 无 BOM」与「LF」。 课里不要求安装转换工具；需要批量处理时，可以搜索「BOM 去除」「CRLF 转 LF」。

用 iconv 转编码

如果手里有一份 GBK 文件，需要转成 UTF-8，可以用 iconv。 它按指定的源编码读取，再按目标编码写出： 

iconv -f GBK -t UTF-8 gbk.txt
相机
分辨率 1280x1024

-f 是源编码（from），-t 是目标编码（to）。 不指定输出文件时，结果写到标准输出，屏幕上看到的就是转换后的文字。 要写成文件，加 -o： 

iconv -f GBK -t UTF-8 gbk.txt -o utf8-new.txt

转换方向不能猜。把已经是 UTF-8 的文件按 GBK 读取，iconv 可能在中途报「非法输入序列」，也可能转出一串错误字符。先用 file 和来源信息确认编码，再转换。iconv -c 会丢弃无法转换的字节， 看起来能跑完，但内容已经缺失，排查问题时不要用。

你现在能做什么：用 file 判断文本的大致编码， 用 od 查看开头字节，认出 BOM 与 CRLF，用 iconv 在 GBK 与 UTF-8 之间转换，并知道乱码多半是编码用错而不是内容损坏。

3.2JSON

JSON（JavaScript Object Notation）是一种用文本表示结构化数据的格式。 配置文件、网络接口、日志里都能见到。它的语法比 YAML 严格，适合程序读写， 也适合人直接检查。这一课看一份相机配置，读它、格式化它， 并处理一处语法错误。

一份 JSON 的结构

config.json 的内容如下： 

{
  "camera": {
    "name": "cam0",
    "resolution": [1280, 1024],
    "fps": 30,
    "exposure_us": 8000,
    "trigger": "software"
  },
  "save": {
    "enabled": true,
    "directory": "data/images",
    "format": "png"
  },
  "calibration": null
}

JSON 只有几种基本结构：对象（object）用花括号表示，里面是「键: 值」对； 数组（array）用方括号表示，里面是一串值；值可以是字符串、数字、布尔值 true/false、null，也可以是另一个对象或数组。 上面这份配置的顶层是一个对象，有两个键：camera 和 save， 它们的值又是对象；calibration 的值是 null， 表示暂时没有标定参数。

键必须用双引号括起来，字符串也必须用双引号。数字不加引号。 对象和数组的最后一个元素后面不能有逗号。JSON 不支持注释。 这几点与 Python 的字面量、JavaScript 的对象写法不同，手写时最容易在这里出错。

从程序里读

Python 标准库自带 json 模块，不需要另装软件。 下面这段程序读取 config.json，打印相机参数： 

import json

with open("config.json", encoding="utf-8") as f:
    config = json.load(f)

camera = config["camera"]
print("相机:", camera["name"])
print("分辨率:", camera["resolution"][0], "x", camera["resolution"][1])
print("帧率:", camera["fps"])
print("曝光:", camera["exposure_us"], "us")
print("触发:", camera["trigger"])

with open(...) as f 打开文件，并在代码块结束时自动关闭； encoding="utf-8" 明确按 UTF-8 读取。json.load(f) 把文件内容解析成 Python 对象：JSON 对象变成字典（dict），数组变成列表（list）， 字符串、数字、布尔值和 null 分别变成 str、 int/float、bool 和 None。

读取时用键取字典的值，用下标取列表的元素：config["camera"] 得到相机对象，camera["resolution"][0] 得到宽度。运行结果： 

cd /tmp/other-basics/示例代码/3.2-JSON
python3 read_config.py
相机: cam0
分辨率: 1280 x 1024
帧率: 30
曝光: 8000 us
触发: software

print 用逗号分隔多个参数时，会在参数之间加一个空格， 所以「分辨率」那一行显示为 1280 x 1024。如果键名写错， 程序会抛出 KeyError；不确定某个键是否存在时， 可以用 config.get("calibration")，键不存在时返回 None，不会中断。

格式化与查错

JSON 文件被压缩成一行时，人很难读。Python 的 json.tool 模块 可以检查语法并按缩进重新输出： 

python3 -m json.tool config.json
{
    "camera": {
        "name": "cam0",
        "resolution": [
            1280,
            1024
        ],
        "fps": 30,
        "exposure_us": 8000,
        "trigger": "software"
    },
    "save": {
        "enabled": true,
        "directory": "data/images",
        "format": "png"
    },
    "calibration": null
}

json.tool 默认用四个空格缩进，把数组的每个元素单独放一行。 它只把结果写到屏幕，不修改原文件；要保存格式化后的版本， 用重定向写入另一个文件。这个命令同时起到校验作用：语法不对时， 它会报错并指出位置。

下面这份 broken.json 少了一个键，末尾还多了一个逗号： 

{
  "name": "cam0",
  "fps": 30,
}

运行同样的命令： 

python3 -m json.tool broken.json
Expecting property name enclosed in double quotes: line 4 column 1 (char 33)

错误信息说，第 4 行第 1 列期望一个用双引号括起来的键名，却遇到了别的内容。 第 4 行是右花括号，问题实际出在第 3 行末尾的逗号：对象最后一个成员后面 不能再有逗号。报错位置有时落在错误的下一个字符上，看到「期望键名」时， 先检查前一行末尾。不同 Python 版本的错误文字可能略有差异， 行号与列号是定位依据。

命令失败时退出码不为 0，可以用 echo $? 查看。 脚本里可以用这一点判断配置文件是否合法：退出码为 0 才继续。

常见语法错误

  • 最后一个成员后面多写逗号：{"a": 1,}、[1, 2,] 都不合法。
  • 用单引号：JSON 只接受双引号，{'a': 1} 不合法。
  • 把注释写进去：JSON 不支持 // 或 # 注释。 需要说明时，可以加一个约定好的键，例如 "_comment"， 并在程序里忽略它。
  • 键没有引号：{a: 1} 不合法，键必须写成 "a"。
  • 重复的键：很多解析器保留最后一个值，也有解析器直接报错；这类问题很难发现， 合并配置时尤其要注意。
  • 特殊数字：NaN、Infinity 不是 JSON 标准的一部分。 Python 的 json 默认能读，但其他语言的解析器可能拒绝； 需要交换数据时不要使用。
  • 数字前导零：01 不合法，应写成 1。

手改配置后，至少运行一次 python3 -m json.tool。 编辑器的高亮只能提示一部分问题，语法检查以解析器的结果为准。

你现在能做什么：读懂嵌套的 JSON 配置，用 Python 的 json 模块取出需要的字段，用 json.tool 格式化并检查语法， 认出逗号、引号、注释这几类常见错误。

3.3YAML

YAML（YAML Ain't Markup Language）是一种以缩进表示层级的配置格式。 它比 JSON 更接近人写笔记的方式，适合手改；ROS 2 的参数、Docker Compose、 持续集成配置都常用 YAML。这一课只要求读懂，不要求安装解析库。

缩进表示层级

下面是一份相机配置 camera.yaml： 

# 相机配置
camera:
  name: cam0
  resolution: [1280, 1024]
  fps: 30
  exposure_us: 8000
  trigger: software
  save:
    enabled: true
    directory: data/images
    format: png

# 标定参数先留空
calibration: null

# 启动时依次执行的步骤
steps:
  - 打开相机
  - 设置曝光
  - 开始采集

notes: |
  第一次运行时先检查设备连接。
  如果画面过暗，增大 exposure_us。

每一行「键: 值」表示一个成员。camera: 后面没有值， 说明它的值是一个嵌套的映射，下面缩进两行的内容都属于它。 save: 又嵌套在 camera 里面，所以它的成员缩进四行。 同一层的键必须对齐；缩进只能用空格，不能用制表符（Tab）。

冒号后面要有一个空格，写成 name: cam0，不能写成 name:cam0。# 开始的是注释，可以单独一行， 也可以写在值后面；解析器会忽略注释。null 表示空值， true/false 表示布尔值。

列表、注释与多行文本

列表的每一项以 - 开头。steps 下面的三项就是列表， 缩进与上一层的键对齐。列表也可以写成方括号形式， resolution: [1280, 1024] 与逐项写两行等价； 短列表写成一行更紧凑。

notes: | 表示后面的缩进文本按原样保留换行，叫做字面块 （literal block）。写多行说明时常用它。另一种写法是 notes: >， 它把相邻的行合并成一段，只在空行处保留换行，叫做折叠块（folded block）。 这两种写法在配置文件里很常见，读到时要看清用的是哪一个。

YAML 的字符串通常不加引号。值里包含冒号加空格、井号、方括号等特殊字符时， 要加引号，例如 title: "相机: cam0"。看起来像数字或布尔值的字符串 也要加引号，避免被解析成别的类型。

yes 与 no 不一定是字符串

YAML 1.1 把 yes、no、on、off 也当作布尔值；YAML 1.2 只把 true、false 当作布尔值。 不同解析器遵循的版本不同。如果某个值确实要表示字符串 yes， 写成 "yes" 最稳妥。需要了解细节时，搜索「YAML 1.1 1.2 布尔值」。

与 JSON 的对应关系

同样一份配置可以写成 JSON。下面是 camera.yaml 对应的 same.json： 

{
  "camera": {
    "name": "cam0",
    "resolution": [1280, 1024],
    "fps": 30,
    "exposure_us": 8000,
    "trigger": "software",
    "save": {
      "enabled": true,
      "directory": "data/images",
      "format": "png"
    }
  },
  "calibration": null,
  "steps": [
    "打开相机",
    "设置曝光",
    "开始采集"
  ],
  "notes": "第一次运行时先检查设备连接。\n如果画面过暗，增大 exposure_us。\n"
}

两种写法表示同一棵树：YAML 的映射对应 JSON 的对象，YAML 的列表对应 JSON 的数组， 标量对应字符串、数字、布尔值或 null。notes 的字面块 在 JSON 里变成一个带 \n 的字符串。YAML 1.2 把 JSON 当作自己的子集， 所以大多数 JSON 文件也可以被 YAML 解析器读取；反过来不一定， 因为 YAML 有注释、锚点等 JSON 没有的写法。

选择哪一种，取决于用途：需要程序之间交换数据、要求严格且工具链统一时，用 JSON； 需要人经常手改、希望写注释时，用 YAML。两者都是文本，都应当用 UTF-8 保存。

读 YAML 时注意什么

  • 缩进必须一致。同一层用同样多的空格；混用空格和 Tab 会直接报错。 编辑器可以设置「Tab 转空格」。
  • 重复的键。有些解析器保留最后一个值，有些直接报错。 合并两份配置时，先确认有没有同名键。
  • 锚点与别名。真实配置里可能出现 &name 定义一段内容、 *name 引用它，以及 << 合并映射。 这些写法用于减少重复；第一次见到时，搜索「YAML 锚点 别名」了解语法即可。
  • 多份文档。一个文件里可以用 --- 分隔多份 YAML 文档， 例如 Kubernetes 配置。读到 --- 时，把它当作另一份配置的开头。
  • 解析器差异。不同语言、不同版本的 YAML 库对布尔值、日期、数字的 处理不完全一样。程序读取配置时，尽量把关键值写成明确的字符串或数字， 避免依赖隐式转换。

Python 标准库不带 YAML 解析器。本课只要求按结构读懂配置文件， 不要求写程序解析；项目里需要读取 YAML 时，再按项目已有的依赖选择库， 并搜索该库的用法。

你现在能做什么：按缩进读出 YAML 的层级，认出映射、列表、注释、 字面块与空值，看懂它与 JSON 的对应关系，并知道缩进、重复键和解析器差异 是常见问题。

3.4Markdown

Markdown 是一种用纯文本写文档的轻量标记语言。文件名通常以 .md 结尾，项目根目录的 README.md 是最常见的一份。平台会把 Markdown 渲染成网页；不渲染时，原文仍然可读。这一课看一份 README，认全常用的几种写法。

这也是组内规范，之后要遵守

这一课不只是通用介绍，也是本组的文档格式规范。从读到这里之后开始， 组内的笔记与项目说明都写成 .md 文件，并按这一课的写法组织： 标题分级，命令放进标注了语言的代码块，文件名与变量用行内代码标出， 链接写相对路径。已有的文档不要求回改。

标题与段落

README.md 的完整内容如下： 

# 计分工具

读取比赛记录，输出每支队伍的总分。

## 用法

```bash
python3 score.py scores.csv
```

## 输入格式

| 列名 | 含义 |
|---|---|
| team | 队伍编号 |
| score | 本轮得分 |

## 说明

详细规则见 [使用说明](docs/usage.md)。

> 注意：分数按整数计算。

- 每行一条记录
- 队伍编号不重复

行首一个 # 是一级标题，两个 ## 是二级标题， 依此类推，最多六级。# 后面要有一个空格。一份文档通常只有一个 一级标题，用作标题；各节用二级标题。标题之间用空行隔开，段落之间也用一个空行 分隔；连续的多行文字会被合并成同一段。

> 开头的是引用块，用来放提示或摘录。引用块可以有多行， 每行都以 > 开头。

列表、强调与链接

无序列表用 -、* 或 + 开头， 选一种并保持一致；有序列表用 1.、2. 开头。 渲染时，有序列表的编号会自动排列，源文件里都写 1. 也可以， 但按顺序写更便于阅读原文。

强调用星号或下划线：**粗体**、*斜体*。 行内代码用反引号包起来，例如 `scores.csv`，适合写文件名、 命令和变量名。链接写成 [显示文字](目标)；目标是相对路径时， 指向仓库里的另一份文件，例如 [使用说明](docs/usage.md)。 图片写成 ![替代文字](图片路径)，替代文字在图片加载失败时显示。

这些标记只有在特定位置才生效：# 要在行首，列表符号要在行首 或缩进后，链接的方括号和圆括号要紧挨着。写在句子中间的星号通常只是普通字符。

代码块与表格

代码块用三个反引号包起来，开头的那一行可以写语言名，渲染时会按该语言着色： 

```bash
python3 score.py scores.csv
```

不写语言名也可以，渲染器会当作普通代码。代码块里的内容按原样显示， 缩进和换行都保留；不要在代码块里再写 Markdown 标记，它们不会被解释。

表格用竖线分隔单元格，第二行是分隔行，用 --- 表示每一列， 冒号控制对齐：---: 右对齐，:--- 左对齐， :---: 居中。表头写第一行，下面逐行写数据。 单元格里的竖线如果属于内容，需要转义；简单的表格通常不会遇到。

表格、任务列表、删除线等写法属于扩展语法，不同平台的支持程度不同。 GitHub 使用的方言叫 GitHub Flavored Markdown（GFM），支持表格和任务列表； 有些简单的渲染器只支持基础语法。写文档时，尽量使用通用写法； 需要确认效果时，在目标平台上预览。

README 的常见结构

先看这份 README 有多少行： 

cd /tmp/other-basics/示例代码/3.4-Markdown
wc -l README.md
25 README.md

再看它有哪些标题： 

grep -n '^#' README.md
1:# 计分工具
5:## 用法
11:## 输入格式
18:## 说明

wc -l 统计行数。grep -n '^#' 找出以 # 开头的行，并显示行号；^ 表示行首，单引号防止 Shell 解释特殊字符。 四个标题把文档分成四节：标题、用法、输入格式、说明。

一个项目的 README 通常回答几个问题：这个项目做什么；怎么安装或准备环境； 怎么运行；输入输出是什么；有哪些限制和注意事项。不是每份 README 都要有 全部小节，但读者应当能在前几行找到「这是什么」和「怎么运行」。 这份 README 先说明用途，再给命令、输入格式和规则，顺序清楚。

写 README 时，命令放在代码块里，文件名和变量用行内代码标出，步骤用有序列表。 这样即使渲染器不支持某些扩展，原文也容易读。

你现在能做什么：读懂 README 的标题层级、列表、链接、代码块与表格， 按结构快速找到用法和输入说明，并按组内规范写出格式正确的 Markdown 笔记与项目说明。

3.5Shell 脚本

Shell 脚本是把一串终端命令写进文本文件，交给 Shell 一次执行。 重复的启动步骤、批量处理文件、定时任务都常用脚本。这一课读懂一个 统计分数的小脚本，知道它怎么取参数、怎么读文件、怎么报告错误； 不要求写复杂脚本。

shebang 与执行权限

脚本的第一行通常是： 

#!/bin/bash

这一行叫 shebang。#! 后面的路径告诉系统用哪个解释器执行这个文件； 这里指定 bash。用 ./summary.sh 直接运行时，系统读取这一行并启动 /bin/bash；用 bash summary.sh 运行时，bash 被显式启动， 这一行只作为注释，但保留它可以让两种方式都可用。shebang 必须在文件第一行， 前面不能有空行或 BOM。

直接运行还需要执行权限。先看脚本当前的权限： 

cd /tmp/other-basics/示例代码/3.5-Shell脚本
stat -c '%A %a %n' summary.sh check_args.sh
-rw-rw-r-- 664 summary.sh
-rw-rw-r-- 664 check_args.sh

stat 的 -c 指定输出格式：%A 是符号形式的权限， %a 是八进制形式，%n 是文件名。664 表示属主和属组可读写，其他用户只读，没有任何执行位。这是这份练习目录里的状态； 从课程文件夹复制时，实际权限还会受 umask 影响。加执行权限： 

chmod +x summary.sh
stat -c '%A %a %n' summary.sh
-rwxrwxr-x 775 summary.sh

chmod +x 给属主、属组和其他用户都加上执行位；从 664 出发， 结果是 775。如果复制后的文件权限不同，结果也会不同。之后可以这样运行： 

./summary.sh

./ 表示当前目录。直接用 summary.sh 不行， 因为当前目录通常不在 PATH 里；PATH 是系统查找命令的 目录列表，前面 Linux 那一部分讲过。用 bash summary.sh 不需要 执行权限，适合在调试时使用；./summary.sh 更接近脚本最终被调用的方式。

变量、参数与引号

下面这个脚本演示位置参数和默认值： 

#!/bin/bash
set -eu

name=${1:-world}
count=${2:-1}

echo "name: $name"
echo "count: $count"

$1 是第一个位置参数，$2 是第二个；$0 是脚本名，$# 是参数个数，$@ 是全部参数。 ${1:-world} 的意思是：如果 $1 没有设置或者为空， 就用 world；否则用 $1 的值。${2:-1} 同理。赋值时等号两边不能有空格，变量名左边不写 $， 使用时才写 $name。

运行时不带参数，两个变量都取默认值；带参数时按顺序填入： 

bash check_args.sh
name: world
count: 1
bash check_args.sh alice 3
name: alice
count: 3

双引号里的变量会被展开，同时保留空格；不加引号的变量在展开后会按空白拆成 多个词。路径和用户输入都可能含空格，所以引用变量时养成加双引号的习惯， 写成 "$name"。单引号里的内容完全不展开，适合写固定字符串。

set -eu 是两个选项：-e 让脚本在某个命令失败时立即退出， -u 让脚本在使用未定义变量时报错退出。它们能防止错误被后续命令掩盖。 代价是某些本来允许失败的命令也要显式处理；读别人的脚本时， 先看有没有这一行。

条件、循环与退出码

完整的统计脚本如下： 

#!/bin/bash
set -eu

file=${1:-scores.txt}

if [ ! -f "$file" ]; then
    echo "找不到文件: $file" >&2
    exit 1
fi

count=0
sum=0
while IFS= read -r line; do
    if [ -z "$line" ]; then
        continue
    fi
    count=$((count + 1))
    sum=$((sum + line))
done < "$file"

echo "条数: $count"
echo "总分: $sum"
echo "平均分: $((sum / count))"

逐段看：

  • file=${1:-...}：把第一个参数赋给 file； 没有参数时用默认的 scores.txt。
  • if [ ! -f "$file" ]; then：[ 是测试命令， -f 判断是不是普通文件，! 取反。方括号内侧要有空格。 文件不存在时，执行下一行。
  • echo ... >&2：把错误信息写到标准错误。标准输出是 文件描述符 1，标准错误是 2；正常结果和错误信息分开，调用者可以只收集正常输出。
  • exit 1：以非零状态退出，表示失败。成功结束时退出码是 0。
  • while IFS= read -r line; do ... done < "$file"： 从文件逐行读取。IFS= 让 read 不修剪行首行尾的空白， -r 让反斜杠按普通字符处理，line 是读到的这一行。 done < "$file" 把文件接到整个循环的标准输入。
  • if [ -z "$line" ]; then continue; fi：-z 判断字符串是否为空；空行跳过，不计数。
  • count=$((count + 1))、sum=$((sum + line))： 算术展开，按整数计算。line 在这里被当作整数；脚本假定每行都是数字， 实际使用时应先检查格式。
  • $((sum / count))：整数除法，小数部分直接舍去。 259 除以 3 得 86，而不是 86.33。全部为空时 count 为 0， 除法会出错；健壮的脚本应先判断 count 是否大于 0。

命令的退出码保存在 $? 里，0 表示成功，非 0 表示失败。 && 和 || 也根据退出码决定是否执行后一条命令； 管道默认只看最后一条命令的退出码。需要逐个检查管道中每条命令的结果时， 可以搜索「bash pipefail」。

完整例子与运行结果

练习目录里的 scores.txt 有三行： 

88
92
79

运行脚本： 

bash summary.sh
条数: 3
总分: 259
平均分: 86

换一个不存在的文件名： 

bash summary.sh missing.txt
找不到文件: missing.txt

脚本在这里以退出码 1 结束。错误信息写到标准错误，所以它不会混进正常输出； 在终端里两者都显示在屏幕上，看起来没有区别。要在脚本里判断上一条命令是否成功， 检查 $? 或使用 if。

加上执行权限后，也可以直接运行： 

chmod +x summary.sh
./summary.sh
条数: 3
总分: 259
平均分: 86

如果 ./summary.sh 报 bad interpreter， 先检查 3.1 讲过的 CRLF；如果报 Permission denied，检查执行位。 用 bash summary.sh 能运行而 ./summary.sh 不能， 通常就是这两类原因。

写脚本的习惯

  • 开头写 shebang，紧跟 set -eu；需要处理管道中任意一段失败时， 再考虑 set -o pipefail。
  • 变量用双引号包起来，尤其是路径和用户输入。
  • 先检查输入文件是否存在、参数个数是否足够，再开始处理。
  • 错误信息写到标准错误，并用非零退出码表示失败；成功时返回 0。
  • 删除、覆盖、移动文件之前，先打印将要操作的路径，确认变量不为空。 不要在脚本里对未检查的变量执行 rm -rf。
  • 用 bash -n summary.sh 检查语法；它只解析，不执行。 更细的检查可以搜索「shellcheck」。
  • 脚本要提交进 Git 时，保持 LF 换行，并确认可执行位被记录。
  • 运行来路不明的脚本之前先读一遍。脚本能执行当前用户的所有操作， 风险与直接运行程序相同。

你现在能做什么：读懂带 shebang、默认参数、条件、循环和退出码的 Shell 脚本，知道 set -eu 与引号的作用，能运行、加执行权限 并定位常见的换行与权限问题。

3.6模型文件

模型文件保存训练得到的权重和网络结构。它不是文本，不能用编辑器读懂； 文件通常很大，格式由训练框架或推理引擎决定。这一课只要求了解三种常见格式、 它们之间的转换关系，以及加载模型时的安全边界。

模型文件里有什么

一个训练好的模型至少包含两部分：结构（有哪些层、层与层怎么连接）和权重 （每一层的参数，通常是大量浮点数）。有的格式还保存优化器状态、训练轮数、 类别名称等元数据。权重没有可读的语义，单独看某个数字没有意义； 它们必须和对应的结构一起使用。

模型文件通常是二进制。用文本编辑器打开会看到乱码，不要试图修改其中的字节。 file 有时能识别出容器类型，例如较新的 PyTorch 保存文件可能是 ZIP 容器，file 会显示 Zip archive data； 但扩展名与内部格式没有严格对应关系，判断格式应当看它由什么工具产生。

三种常见格式

格式常见来源特点与用途
.pt / .pth PyTorch 的 torch.save 保存张量、模型参数，也可能包含 Python 对象；用 torch.load 读取；适合训练与继续开发，不适合跨框架交换
.onnx PyTorch、TensorFlow 等导出 开放神经网络交换格式（Open Neural Network Exchange）；用 protobuf 描述计算图和权重；可被 ONNX Runtime、TensorRT 等读取；适合跨框架部署
.engine NVIDIA TensorRT 构建 针对特定 GPU、软件版本和输入尺寸编译出的执行计划；在同一环境中 推理速度快；不可移植，换环境要重新构建

几个名词先说明：pickle 是 Python 的对象序列化格式，torch.save 常用它保存模型；protobuf（Protocol Buffers）是一种二进制的结构化数据格式， ONNX 用它描述计算图；TensorRT 是 NVIDIA 的推理优化库，把模型编译成显卡上的 执行计划。需要细节时，分别搜索「PyTorch 保存加载模型」「ONNX 格式」 「TensorRT engine」。

扩展名只是惯例。.pth 既可能保存整个模型，也可能只保存参数字典 （state_dict）；.pt 也可能是 TorchScript 或 ZIP 包。 拿到文件后，先问清楚它是怎么产生的、用什么代码加载，不要仅凭后缀判断。

转换链：pt 到 onnx 到 engine

常见的部署流程是：在 PyTorch 里训练，导出 ONNX，再在目标机器上构建 TensorRT engine。三步的关系可以画成： 

PyTorch 训练
  └─ model.pt
       │  torch.onnx.export
       ▼
     model.onnx
       │  TensorRT 构建（trtexec 或 API）
       ▼
     model.engine

下面是一段导出 ONNX 的示意代码。它需要安装 PyTorch，本课不要求运行： 

# 仅示意：运行需要安装 PyTorch。
import torch

model = torch.nn.Linear(4, 2)
example = torch.randn(1, 4)

torch.onnx.export(
    model,
    example,
    "model.onnx",
    input_names=["input"],
    output_names=["output"],
    opset_version=17,
)

example 是一份形状和数据类型都正确的示例输入，导出器沿着这次计算 记录网络结构；输入形状不固定时，还要指定动态维度。input_names 和 output_names 给输入输出起名字，部署时按这些名字传数据。 opset_version 是 ONNX 算子集版本，导出端和运行端都要支持这个版本； 版本过高可能没有运行时支持，过低可能缺少需要的算子。具体对应关系需要查 导出工具与推理框架的文档。

转换不保证完全等价。自定义算子、动态控制流、训练专用的层都可能导出失败， 或者导出后结果不一致。转换完成后，应当用同一批输入分别跑原模型和转换后的模型， 比较输出的最大误差；不能只看文件是否生成成功。

构建 engine 通常用 TensorRT 自带的 trtexec，也可以在程序里调用 TensorRT 的 API。示意命令如下，需要安装 TensorRT；本课不要求运行： 

trtexec --onnx=model.onnx --saveEngine=model.engine

构建时要指定精度（FP32、FP16、INT8）、最大批量、输入尺寸范围等参数。 这些参数会影响速度和显存占用，也会影响结果精度。engine 与构建时的 GPU 型号、 TensorRT 版本、CUDA 版本、驱动版本绑定，所以通常在实际部署的机器上构建。

engine 为什么不能随便打开

不要随意反序列化来路不明的模型文件

torch.load 读取 .pt 时可能使用 pickle。pickle 在 反序列化时可以构造任意 Python 对象，恶意文件因此有机会执行代码。 TensorRT engine 的加载同样会调用本地库和插件，文件损坏或来源不可信时 可能导致崩溃，甚至执行非预期操作。把字节重新变成程序里的对象， 这个过程叫反序列化（deserialize）；反序列化不是「只读数据」， 它可能触发代码。

只加载自己构建、或者来源可信并且校验过完整性的模型。不要双击打开陌生的 .pt、.engine，不要把用户上传的模型直接交给生产服务 加载，也不要在没有隔离的机器上试跑。较新的 PyTorch 提供 weights_only=True 选项，限制反序列化时允许的对象类型； 它降低风险，但不能替代对来源的检查。具体行为随版本变化， 使用前查对应版本的文档。

.engine 还有一层限制：它是为特定环境编译的，不是通用模型文件。 把一台机器上的 engine 复制到另一台机器，即使文件名相同，也可能加载失败 或结果错误。需要迁移时，应当带上 ONNX 或原始权重，在目标机器上重新构建。 不要把它当作可以随意分发的模型。

模型文件属于二进制资产，通常不提交进 Git 仓库。前面 Git 那一部分讲过 忽略权重目录；需要共享时，用专门的文件存储或制品库，并记录版本与校验和。 常见做法是计算 SHA-256 校验和，接收方核对后再使用；sha256sum 的用法可以自行搜索。

拿到模型文件先确认什么

  • 来源与许可：谁训练的、基于什么数据、允许什么用途。来源不明的权重 不要用于正式任务。
  • 输入输出：输入的形状、数据类型、颜色顺序、归一化方式；输出的含义、 类别顺序、是否包含后处理。这些信息通常写在 README 或单独的配置里。
  • 版本：训练框架版本、ONNX opset、TensorRT 与 CUDA 版本、GPU 型号。 版本不匹配是转换和加载失败的主要原因之一。
  • 完整性：文件大小与校验和是否与提供方一致。传输中断产生的半个文件， 加载时可能报出难以理解的错误。
  • 数值：用一份已知输入跑一遍，和提供方的结果比较。只看程序不报错不够， 结果正确才算可用。

你现在能做什么：分清 .pt、.onnx、 .engine 三种格式的用途与来源，读懂导出 ONNX 的关键参数， 知道 engine 与运行环境绑定，并明白来路不明的模型文件不能随意反序列化。

3.7日志

日志是程序运行时写下的文本记录。程序出错、结果不对、服务起不来， 第一手线索通常都在日志里。这一课看一份相机程序的日志， 学会按时间、级别和模块定位问题。

一行日志的组成

先看日志的前三行： 

cd /tmp/other-basics/示例代码/3.7-日志
head -n 3 app.log
2026-03-14 09:00:01 INFO  camera: 打开设备 cam0
2026-03-14 09:00:01 INFO  camera: 分辨率 1280x1024, 帧率 30
2026-03-14 09:00:02 WARN  camera: 曝光时间 8000 us 偏大

每一行由几部分组成：日期、时间、级别、模块名和消息。前两列是时间戳； 第三列是级别；camera: 是写日志的模块；后面是具体内容。 这不是所有日志的统一格式，而是这份程序采用的格式。有的程序写成 JSON， 一行一个对象；有的把级别放在方括号里；有的把时间放在行尾。 读一份新日志时，先看前几行，找出各列的含义。

看文件规模： 

wc -l app.log
11 app.log
wc -c app.log
584 app.log

11 行，584 字节。行数少不代表内容少：一行里可能包含很长的错误信息； 字节数还会因为中文而增大，一个汉字在 UTF-8 里占三个字节。 排查问题时，两个数字都只能作为规模参考。

日志级别

常见的级别从低到高是：

级别含义通常怎么处理
DEBUG调试细节，例如每一步的中间值 开发时打开，正式运行时通常关闭，避免日志过多
INFO正常事件，例如启动、连接成功、保存完成 保留，用来还原程序做过什么
WARN异常但程序还能继续，例如参数偏大、磁盘将满 查看是否需要调整配置或提前处理
ERROR某个操作失败，例如写入失败、请求超时 优先排查；程序可能继续运行，也可能退出
FATAL严重错误，程序无法继续 立即处理，通常伴随进程退出

级别是约定，不是语法。不同程序可能使用 CRITICAL、 WARNING 等等价名称，也可能只有 INFO 和 ERROR 两档。 日志级别通常有一个阈值：设为 INFO 时，DEBUG 不输出；设为 WARN 时， INFO 也不输出。日志太多时，先调整阈值，而不是删除已有的日志。

看到 ERROR 不要立刻下结论。这份日志里，第 5 行报告丢帧，第 6 行就恢复了采集； 第 9 行写入失败，第 10 行重试成功。单看一行会误判，必须看它前后的几行。

看最近的、找错误的

程序正在运行时，最常看的是文件末尾： 

tail -n 3 app.log
2026-03-14 09:02:00 ERROR save: 写入失败: 权限不足
2026-03-14 09:02:01 INFO  save: 重试成功
2026-03-14 09:03:00 INFO  camera: 关闭设备 cam0

tail -n 3 显示最后三行。tail -f app.log 会持续输出新追加的内容，适合盯着正在运行的程序；按 Ctrl+C 结束。 如果日志会被轮转，tail -F app.log 会在文件改名后按名字重新打开， 比 -f 更适合长期观察。

要找所有错误行： 

grep ERROR app.log
2026-03-14 09:00:10 ERROR capture: 丢帧 3 帧
2026-03-14 09:02:00 ERROR save: 写入失败: 权限不足

grep 默认区分大小写，匹配 ERROR 不会匹配 error。加上 -n 显示行号，便于回到原文件查看上下文： 

grep -n ERROR app.log
5:2026-03-14 09:00:10 ERROR capture: 丢帧 3 帧
9:2026-03-14 09:02:00 ERROR save: 写入失败: 权限不足

统计某个级别出现多少次，可以用 grep -c： 

grep -c WARN app.log
2

-c 统计的是匹配的行数，不是匹配次数。一行里出现两次 WARN，也只算一行。grep 在没有匹配时退出码是 1， 在脚本里配合 set -e 使用时要注意这一点。

要看某一行前后的内容，可以用 sed 按行号打印。 例如查看第 5 行前后： 

sed -n '4,6p' app.log
2026-03-14 09:00:03 INFO  capture: 开始采集
2026-03-14 09:00:10 ERROR capture: 丢帧 3 帧
2026-03-14 09:00:11 INFO  capture: 恢复采集

sed -n 默认不打印，'4,6p' 表示打印第 4 到第 6 行。 sed 的完整用法超出本课范围，需要时搜索「sed 按行号打印」。

统计与定位

如果想知道每个级别各有多少行，可以按第三列分组统计： 

awk '{print $3}' app.log | sort | uniq -c
      2 ERROR
      7 INFO
      2 WARN

awk 按行读入，默认以空白分隔字段；$1 是日期， $2 是时间，$3 是级别，$4 是模块名。 {print $3} 只输出第三列。管道把结果交给 sort 排序， 再交给 uniq -c 统计相邻的重复行。uniq 只合并相邻的 相同行，所以必须先排序；不排序时，同一种级别分散在文件各处， 会被统计成多行。

输出里的数字在左边，级别在右边，数字前的空格是 uniq -c 的对齐格式。把命令里的 $3 换成 $4，就能按模块统计； 换成 $1，可以按日期统计。字段编号从 1 开始，$0 表示整行。

定位问题时，常用的顺序是：先用 grep -n ERROR 找到错误行号， 再用 sed -n 看前后几行，最后用 grep 搜同一个模块 或同一段时间的其他记录。不要只看错误行本身；上下文通常说明了错误发生前 发生了什么。

轮转与长期保存

日志会不断增长，不能一直写进同一个文件。常见的做法是轮转（rotation）： 当前文件写满一天或一定大小后，改名为 app.log.1，新建一个空的 app.log；旧的 app.log.1 再改名为 app.log.2，依此类推，超过保留数量的文件被删除或压缩。 练习目录里有一份旧的 app.log.1： 

2026-03-13 18:20:00 INFO  camera: 打开设备 cam0
2026-03-13 18:20:01 INFO  capture: 开始采集
2026-03-13 18:30:00 WARN  disk: 剩余空间 3.4 GB
2026-03-13 18:40:00 INFO  camera: 关闭设备 cam0

它的时间比 app.log 早，说明是前一天留下的。Linux 上常用的 轮转工具叫 logrotate，它按配置定期执行改名、压缩和删除；配置通常放在 /etc/logrotate.d 下。压缩后的日志以 .gz 结尾， 可以用 zcat 直接查看，用 zgrep 直接搜索， 不需要先解压。需要自己配置时，搜索「logrotate 配置」。

轮转也带来一个细节：tail -f app.log 跟着的是打开时的那个文件， 文件改名后它可能继续读旧文件；tail -F app.log 会按文件名重新打开， 适合跨轮转观察。长时间盯日志时用 -F。

日志里可能包含路径、用户名、IP 地址、设备编号，甚至令牌。把日志发给别人 或贴到公开页面之前，先删除或替换这些内容；只保留复现问题所需的部分。 日志的保留时间也要有规定：留得太短，出了问题查不到；留得太久， 占用磁盘并增加泄露风险。

你现在能做什么：按时间与级别读取日志，用 tail、 grep、sed、awk 找到错误和上下文， 统计各级别数量，理解轮转文件的命名与 tail -F 的用途， 并在分享日志前清理敏感内容。
