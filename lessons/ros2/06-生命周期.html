第 6 部分

生命周期

普通节点创建后立即开始工作，生命周期（lifecycle）节点则把启动过程拆成 配置、激活、停用与清理几个有名字的状态。状态由服务驱动，节点可以在 未激活时保留资源，也可以在激活后才对外发布或订阅。这一部分先看状态机， 再写生命周期节点与管理节点，最后把启动顺序放进 launch 文件。

终端位置

本页命令默认在课程工作空间 $HOME/ros2_ws 中执行；开头标有 # 当前目录：课程目录 的命令在本页所在目录执行，该目录包含 示例代码/。新开终端先进入工作空间并加载环境： 

# 当前目录：$HOME/ros2_ws
cd $HOME/ros2_ws
source /opt/ros/jazzy/setup.bash
source install/setup.bash
export ROS_DOMAIN_ID=42
export RCUTILS_CONSOLE_OUTPUT_FORMAT='[{severity}] [{name}]: {message}'

需要清掉旧的构建产物时，在 $HOME/ros2_ws 中执行下面的命令， 再重新构建： 

# 当前目录：$HOME/ros2_ws
bash clean.sh
前置

先读过 1.1、1.2、2.2 与 5.1–5.3：会写发布者与订阅者，会声明节点参数， 会写 XML 启动文件。生命周期节点沿用这些接口，只把创建与启动的时机 分开。

6.1生命周期与状态机

生命周期（lifecycle）是节点的一组约定状态。节点创建后先处于未配置状态， 收到配置请求才申请资源；收到激活请求后才开始发布、订阅或驱动硬件； 停用后保留资源但停止对外工作；清理后释放资源，回到未配置。 这些状态与允许的转换构成一个状态机（state machine）。

状态机的价值在于把“对象已经创建”和“对象可以工作”分开。构造函数只做 不会失败或容易回滚的初始化；打开设备、分配大块内存、建立连接放到配置 回调；真正开始发布与接收放到激活回调。启动失败时，节点停在未激活状态， 上层可以重试、换参数或安全退出。

四个状态

主状态有四个。unconfigured 表示节点已创建，但还没有申请 工作资源；inactive 表示资源已经就绪，但节点不对外发布、 不接收消息；active 表示节点正在工作；finalized 表示节点已经关闭，不能再回到前面的状态。

状态之间还有短暂的过渡状态，例如正在配置时的 configuring、 正在激活时的 activating。命令行查询通常只看到稳定后的主状态； ros2 lifecycle list 会把这些过渡状态写成目标的名称。

状态转换

转换（transition）由生命周期服务触发，常用的有五个： configure 从 unconfigured 进入 inactive；activate 从 inactive 进入 active；deactivate 从 active 回到 inactive；cleanup 从 inactive 回到 unconfigured； shutdown 从任一主状态进入 finalized。

每个生命周期节点提供三个服务：<节点名>/change_state 请求转换，<节点名>/get_state 查询当前状态， <节点名>/get_available_transitions 列出当前可用的转换。 命令行工具 ros2 lifecycle 封装了这三个服务。

何时使用

需要控制启动时机的节点适合使用生命周期：传感器驱动要在标定完成后才 开始发布，控制器要等上游节点就绪后才激活，调试时希望暂停某个节点而不 销毁它。普通计算节点不需要这层结构，直接继承 rclcpp::Node 更简单。

例题 · 走一遍状态

终端一启动生命周期节点 lifecycle_talker。终端二先查询初始 状态，再依次发送 configure 与 activate， 每次转换后查询一次。方括号里的数字是状态编号。 

# 终端一（$HOME/ros2_ws）
ros2 run robot_nodes lifecycle_talker
# 终端二（$HOME/ros2_ws）
ros2 lifecycle get /lifecycle_talker
ros2 lifecycle set /lifecycle_talker configure
ros2 lifecycle get /lifecycle_talker
ros2 lifecycle set /lifecycle_talker activate
ros2 lifecycle get /lifecycle_talker
unconfigured [1]
inactive [2]
active [3]

第一行来自刚启动的节点；配置成功后进入 inactive，激活后 进入 active。ros2 lifecycle set 自己会打印 转换结果，这里只保留 get 的三行输出。

启动 lifecycle_talker，先打印一次初始状态，再依次执行 configure、activate、deactivate 与 cleanup，每次转换后打印状态。

inactive [2]
active [3]
inactive [2]
unconfigured [1]
看答案

节点启动后先打印初始状态，再对四个转换各发一次请求，每次请求后读回状态。 脚本在节点服务出现后才开始，避免第一条命令落在服务尚未注册的时候。

sleep 1

inactive [2]
active [3]
inactive [2]
unconfigured [1]

状态依次是 unconfigured、inactive、 active、inactive、unconfigured。 cleanup 回到起点，节点仍可再次配置。

6.2生命周期节点

生命周期节点继承 rclcpp_lifecycle::LifecycleNode，并覆盖 配置、激活、停用、清理与关闭回调。构造函数只声明参数、创建定时器； 需要资源的操作放进 on_configure，开始对外工作的操作放进 on_activate。

类与回调

五个回调的返回类型都是 rclcpp_lifecycle::node_interfaces::LifecycleNodeInterface::CallbackReturn， 通常简写为 CallbackReturn。返回 SUCCESS 表示 转换完成；返回 FAILURE 表示转换失败，节点留在原状态； 返回 ERROR 会把节点带入错误处理流程。回调里不要抛出异常， 失败要通过返回值报告。

LifecycleNode 不是 rclcpp::Node，不能直接交给 rclcpp::spin。主函数要用 rclcpp::spin(node->get_node_base_interface())， 把节点的基础接口交给执行器。

生命周期发布者

生命周期节点里的发布者通常写成 rclcpp_lifecycle::LifecyclePublisher。它在 on_configure 中创建，在 on_activate 中显式调用 on_activate()，在 on_deactivate 中调用 on_deactivate()。定时器每次发布前检查 publisher_->is_activated()；未激活时直接返回，不产生消息。

这一层检查不能省。节点的激活回调被覆盖后，生命周期发布者不会自动跟着 激活；只把节点状态改成 active，发布者仍然关闭，消息不会发出。

运行与查询

节点启动后处于 unconfigured。用 ros2 lifecycle set 发送转换，用 ros2 lifecycle get 查询状态。下面的源码把话题、周期、消息内容与激活失败开关都做成参数， 便于在命令行改变行为。 

#include <chrono>
#include <memory>
#include <string>

#include "rclcpp/rclcpp.hpp"
#include "rclcpp_lifecycle/lifecycle_node.hpp"
#include "std_msgs/msg/string.hpp"

using CallbackReturn =
  rclcpp_lifecycle::node_interfaces::LifecycleNodeInterface::CallbackReturn;

class LifecycleTalker : public rclcpp_lifecycle::LifecycleNode
{
public:
  LifecycleTalker()
  : LifecycleNode("lifecycle_talker")
  {
    topic_ = declare_parameter<std::string>("topic", "chatter");
    period_ms_ = declare_parameter<int>("period_ms", 500);
    message_ = declare_parameter<std::string>("message", "active");
    fail_on_activate_ = declare_parameter<bool>("fail_on_activate", false);

    timer_ = create_wall_timer(
      std::chrono::milliseconds(period_ms_), [this]() {
        if (!publisher_ || !publisher_->is_activated()) {
          return;
        }
        std_msgs::msg::String message;
        message.data = message_;
        publisher_->publish(message);
      });
  }

  CallbackReturn on_configure(const rclcpp_lifecycle::State &) override
  {
    publisher_ = create_publisher<std_msgs::msg::String>(topic_, 10);
    RCLCPP_INFO(get_logger(), "configured: message='%s'", message_.c_str());
    return CallbackReturn::SUCCESS;
  }

  CallbackReturn on_activate(const rclcpp_lifecycle::State &) override
  {
    if (fail_on_activate_) {
      RCLCPP_ERROR(get_logger(), "activation refused");
      return CallbackReturn::FAILURE;
    }
    publisher_->on_activate();
    RCLCPP_INFO(get_logger(), "activated");
    return CallbackReturn::SUCCESS;
  }

  CallbackReturn on_deactivate(const rclcpp_lifecycle::State &) override
  {
    publisher_->on_deactivate();
    RCLCPP_INFO(get_logger(), "deactivated");
    return CallbackReturn::SUCCESS;
  }

  CallbackReturn on_cleanup(const rclcpp_lifecycle::State &) override
  {
    publisher_.reset();
    RCLCPP_INFO(get_logger(), "cleaned up");
    return CallbackReturn::SUCCESS;
  }

  CallbackReturn on_shutdown(const rclcpp_lifecycle::State &) override
  {
    publisher_.reset();
    RCLCPP_INFO(get_logger(), "shut down");
    return CallbackReturn::SUCCESS;
  }

private:
  std::string topic_;
  int period_ms_;
  std::string message_;
  bool fail_on_activate_;
  rclcpp_lifecycle::LifecyclePublisher<std_msgs::msg::String>::SharedPtr publisher_;
  rclcpp::TimerBase::SharedPtr timer_;
};

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  auto node = std::make_shared<LifecycleTalker>();
  rclcpp::spin(node->get_node_base_interface());
  rclcpp::shutdown();
  return 0;
}

练习 6-4

启动 lifecycle_talker，配置并激活后读取一条 /chatter 消息；再停用，等待一秒后重新读取。第二次读取没有消息时打印 no message。

active
no message
看答案

激活后生命周期发布者打开，定时器每 500 毫秒发布一次 active；停用后发布者关闭，定时器仍在运行但不再发布。 第一次读取用 head -n1 去掉 topic echo 的 分隔线，第二次读取超时后打印 no message。 

# 当前目录：$HOME/ros2_ws
ros2 run robot_nodes lifecycle_talker >/dev/null 2>&1 &
sleep 1
ros2 lifecycle set /lifecycle_talker configure >/dev/null
ros2 lifecycle set /lifecycle_talker activate >/dev/null
timeout 3 ros2 topic echo --once --field data /chatter 2>/dev/null \
  | head -n1
ros2 lifecycle set /lifecycle_talker deactivate >/dev/null
sleep 0.7
timeout 1.5 ros2 topic echo --once --field data /chatter 2>/dev/null \
  || echo 'no message'
active
no message

第一段输出 active；停用后没有新消息，第二次读取超时。 这说明发布者的开关跟着生命周期状态变化，而不是跟着节点进程是否存活。

你现在能写什么：继承 LifecycleNode，在配置回调里创建生命周期发布者，在激活与停用回调里开关它，并让定时器只在发布者激活时发送消息。

6.3生命周期管理节点

生命周期节点不会自己转换状态，需要有调用者发送服务请求。管理节点 （manager node）是普通 rclcpp::Node，为每个被管理的节点创建 一个 lifecycle_msgs/srv/ChangeState 客户端，按给定顺序调用 change_state。

管理节点

转换名称在命令行里是字符串，在服务里是编号。 lifecycle_msgs/msg/Transition 定义了 TRANSITION_CONFIGURE、TRANSITION_ACTIVATE、 TRANSITION_DEACTIVATE 与 TRANSITION_CLEANUP 等常量；请求的 transition.id 填常量，服务返回 success 表示转换是否完成。

管理节点在启动时用 wait_for_service 等每个 <节点名>/change_state 出现。被管理的节点可能比管理 节点晚启动，等待服务比固定睡眠可靠。

启动顺序

下面的实现按参数 nodes 给出的顺序配置全部节点，再按同一 顺序激活；激活之间留 gap_ms 毫秒，让发现与连接有时间完成。 保持 hold_ms 毫秒后，按相反顺序停用，再按相反顺序清理。 依赖方排在前面，因此激活时上游先就绪，停用时下游先停下。

失败处理

任何一步返回失败，管理节点打印 stopped after failure 并停止， 不再执行后面的转换。已经激活的节点保持在原状态，便于检查现场。放进 launch 文件时，管理节点设 on_exit="shutdown"，管理节点退出 后启动器关闭其余进程。 

#include <chrono>
#include <map>
#include <memory>
#include <sstream>
#include <string>
#include <vector>

#include "lifecycle_msgs/msg/transition.hpp"
#include "lifecycle_msgs/srv/change_state.hpp"
#include "rclcpp/rclcpp.hpp"

using namespace std::chrono_literals;
using Transition = lifecycle_msgs::msg::Transition;

class LifecycleManager : public rclcpp::Node
{
public:
  LifecycleManager()
  : Node("lifecycle_manager")
  {
    nodes_ = split(declare_parameter<std::string>("nodes", ""));
    hold_ms_ = declare_parameter<int>("hold_ms", 1200);
    gap_ms_ = declare_parameter<int>("gap_ms", 300);
    for (const auto & node : nodes_) {
      clients_[node] = create_client<lifecycle_msgs::srv::ChangeState>(
        node + "/change_state");
    }
  }

  bool run()
  {
    if (nodes_.empty()) {
      RCLCPP_ERROR(get_logger(), "parameter 'nodes' is empty");
      return false;
    }

    for (const auto & node : nodes_) {
      if (!clients_[node]->wait_for_service(3s)) {
        RCLCPP_ERROR(get_logger(), "%s/change_state is not available", node.c_str());
        return false;
      }
    }

    for (const auto & node : nodes_) {
      if (!change(node, Transition::TRANSITION_CONFIGURE, "configure")) {
        RCLCPP_ERROR(get_logger(), "stopped after failure");
        return false;
      }
    }
    for (const auto & node : nodes_) {
      if (!change(node, Transition::TRANSITION_ACTIVATE, "activate")) {
        RCLCPP_ERROR(get_logger(), "stopped after failure");
        return false;
      }
      rclcpp::sleep_for(std::chrono::milliseconds(gap_ms_));
    }

    rclcpp::sleep_for(std::chrono::milliseconds(hold_ms_));

    for (auto it = nodes_.rbegin(); it != nodes_.rend(); ++it) {
      if (!change(*it, Transition::TRANSITION_DEACTIVATE, "deactivate")) {
        RCLCPP_ERROR(get_logger(), "stopped after failure");
        return false;
      }
    }
    for (auto it = nodes_.rbegin(); it != nodes_.rend(); ++it) {
      if (!change(*it, Transition::TRANSITION_CLEANUP, "cleanup")) {
        RCLCPP_ERROR(get_logger(), "stopped after failure");
        return false;
      }
    }

    RCLCPP_INFO(get_logger(), "done");
    return true;
  }

private:
  static std::vector<std::string> split(const std::string & text)
  {
    std::vector<std::string> out;
    std::istringstream stream(text);
    std::string item;
    while (std::getline(stream, item, ',')) {
      if (!item.empty()) {
        out.push_back(item);
      }
    }
    return out;
  }

  bool change(const std::string & node, uint8_t id, const char * action)
  {
    auto request = std::make_shared<lifecycle_msgs::srv::ChangeState::Request>();
    request->transition.id = id;
    auto future = clients_[node]->async_send_request(request);
    const auto code = rclcpp::spin_until_future_complete(
      shared_from_this(), future, 2s);
    if (code != rclcpp::FutureReturnCode::SUCCESS) {
      RCLCPP_ERROR(get_logger(), "%s %s: service call failed", action, node.c_str());
      return false;
    }
    if (!future.get()->success) {
      RCLCPP_ERROR(get_logger(), "%s %s: failed", action, node.c_str());
      return false;
    }
    RCLCPP_INFO(get_logger(), "%s %s: success", action, node.c_str());
    return true;
  }

  std::vector<std::string> nodes_;
  int hold_ms_;
  int gap_ms_;
  std::map<std::string, rclcpp::Client<lifecycle_msgs::srv::ChangeState>::SharedPtr>
  clients_;
};

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  auto manager = std::make_shared<LifecycleManager>();
  manager->run();
  rclcpp::shutdown();
  return 0;
}

终端一启动节点 alpha，终端二让管理节点只管理它。管理节点 配置、激活、等待一小段时间，再停用并清理，最后打印 done。

# 终端二（$HOME/ros2_ws）

[INFO] [lifecycle_manager]: deactivate /alpha: success

练习 6-5

启动 alpha 与 beta 两个生命周期节点，话题分别为 /alpha 与 /beta。用管理节点管理 /alpha,/beta，hold_ms:=300、gap_ms:=200。

[INFO] [lifecycle_manager]: configure /alpha: success
[INFO] [lifecycle_manager]: configure /beta: success

练习 6-6

启动 alpha 与 faulty，其中 faulty 设 fail_on_activate:=true。用管理节点管理 /alpha,/faulty，观察失败后管理节点是否继续。

[INFO] [lifecycle_manager]: configure /alpha: success
[INFO] [lifecycle_manager]: configure /faulty: success
[INFO] [lifecycle_manager]: activate /alpha: success
[ERROR] [lifecycle_manager]: activate /faulty: failed
[ERROR] [lifecycle_manager]: stopped after failure
[ERROR] [faulty]: activation refused
看答案

faulty 的 on_activate 返回 CallbackReturn::FAILURE，服务响应里的 success 为假。管理节点在激活 faulty 时停止， 不再发送停用与清理请求，已经激活的 alpha 留在激活状态。 

# 当前目录：$HOME/ros2_ws
ros2 run robot_nodes lifecycle_talker \
  --ros-args -r __node:=alpha -p topic:=/alpha >/dev/null 2>&1 &
ros2 run robot_nodes lifecycle_talker \
  --ros-args -r __node:=faulty -p topic:=/faulty \
  -p fail_on_activate:=true >/tmp/faulty.log 2>&1 &
sleep 1
ros2 run robot_nodes lifecycle_manager \
  --ros-args -p nodes:=/alpha,/faulty -p hold_ms:=300 -p gap_ms:=200
grep 'activation refused' /tmp/faulty.log
[INFO] [lifecycle_manager]: configure /alpha: success
[INFO] [lifecycle_manager]: configure /faulty: success
[INFO] [lifecycle_manager]: activate /alpha: success
[ERROR] [lifecycle_manager]: activate /faulty: failed
[ERROR] [lifecycle_manager]: stopped after failure
[ERROR] [faulty]: activation refused

activate /faulty: failed 与管理节点的 stopped after failure 是同一件事的两侧：服务端拒绝转换， 管理节点收到失败的响应后停止。

你现在能写什么：写一个普通节点作为管理器，为多个生命周期节点建立 ChangeState 客户端，按列表顺序配置与激活、按相反顺序停用与清理，并在一步失败时停止。

6.4启动文件与启动顺序

生命周期节点、订阅者与管理节点可以放进同一个 launch 文件。启动器负责 创建进程；状态转换仍由管理节点按列表执行。启动文件的进程顺序不等于 状态顺序，真正决定先激活谁的是管理节点的 nodes 参数。

启动文件

下面的文件先启动监听者与发布者，再启动管理节点。管理节点的 on_exit="shutdown" 让启动器在管理节点结束后关闭整个启动 系统；nodes 把监听者排在发布者前面，gap_ms 给激活之间留出间隔。 

<launch>
  <node pkg="robot_nodes" exec="lifecycle_listener"
        name="lifecycle_listener" output="screen"/>
  <node pkg="robot_nodes" exec="lifecycle_talker"
        name="lifecycle_talker" output="screen"/>
  <node pkg="robot_nodes" exec="lifecycle_manager"
        name="lifecycle_manager" output="screen" on_exit="shutdown">
    <param name="nodes" value="/lifecycle_listener,/lifecycle_talker"/>
    <param name="hold_ms" value="1500"/>
    <param name="gap_ms" value="300"/>
  </node>
</launch>

顺序与依赖

管理节点先等待两个 change_state 服务，再按 nodes 的顺序配置。激活也按同一顺序：监听者先激活，发布者 后激活，发布者的第一批消息不会落空；停用时反过来，发布者先停，监听者 后停，发布者先停止发送，监听者再结束订阅。

管理节点在激活之间睡眠 gap_ms 毫秒，是为了让 DDS 发现 完成。真实系统里这个值要按网络与节点数量调整；它不替代 wait_for_service，后者只保证服务出现，不保证话题连接已经 建立。

检查话题端点

生命周期发布者在配置时创建，在激活时打开；生命周期订阅者在激活时才 创建。因此可以在不同阶段用 ros2 topic info 看端点数量： 两个节点都只配置、不激活时，发布者已经存在，订阅者还不存在。

练习 6-8

启动 lifecycle_talker 与 lifecycle_listener，只对两者发送 configure，打印 /chatter 的发布者与订阅者数量。

Publisher count: 1
Subscription count: 0
看答案

两个节点都只配置、不激活。发布者在 on_configure 中创建， 所以计数为 1；订阅者在 on_activate 中才创建，所以计数为 0。 

# 当前目录：$HOME/ros2_ws
ros2 run robot_nodes lifecycle_talker >/dev/null 2>&1 &
ros2 run robot_nodes lifecycle_listener >/dev/null 2>&1 &
sleep 1
ros2 lifecycle set /lifecycle_talker configure >/dev/null
ros2 lifecycle set /lifecycle_listener configure >/dev/null
sleep 0.3
ros2 topic info /chatter | grep -E '^(Publisher|Subscription) count'
Publisher count: 1
Subscription count: 0

再对两个节点发送 activate，订阅计数才会变成 1。端点数量 因此可以用来判断生命周期节点当前是否已经激活。

你现在能写什么：把生命周期节点与管理节点放进 launch 文件，用 on_exit="shutdown" 收尾，并通过管理节点的列表控制配置、激活、停用与清理的顺序。
