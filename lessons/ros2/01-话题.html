话题

1.1发布者

发布者（publisher）把消息写入一个话题（topic）。它不关心谁在接收， 也不等待接收方；消息进入中间件后，已经连接的订阅者各自取走一份。 这一课写一个每 500 毫秒发布一条字符串的节点，并在三次之后停止。

创建发布者

发布者的类型由消息类型决定。下面这行创建一个 std_msgs::msg::String 的发布者，话题名是 chatter，队列深度是 10： 

publisher_ = create_publisher<std_msgs::msg::String>("chatter", 10);

话题名 chatter 没有前导斜杠，是相对名称；节点在 / 命名空间下时，它解析成 /chatter。若节点被放进 /robot1，同一个相对名称解析成 /robot1/chatter。 第二个参数 10 是历史深度：队列满时保留最近的 10 条，旧的被丢弃。

publisher_ 是 rclcpp::Publisher<…>::SharedPtr。 发布者句柄必须活得比使用它的回调长；把它存成节点成员，节点析构时句柄 才释放。若只在构造函数里创建局部句柄，构造结束句柄就销毁，之后发布不会 到达任何订阅者。

消息与定时器

消息是普通对象。先声明 std_msgs::msg::String message，再给 message.data 赋值，最后传给 publish。发布之后 修改同一个对象不会改变已经发出的消息；中间件在调用时完成序列化或复制。

定时器回调每 500 毫秒执行一次。计数在发布之后自增，达到 3 时关闭节点， 因此输出三行，内容分别是 hello 0、hello 1 与 hello 2。日志写在发布之后，看到一行日志就说明那一条消息 已经交给中间件。 

#include <chrono>
#include <memory>
#include <string>

#include "rclcpp/rclcpp.hpp"
#include "std_msgs/msg/string.hpp"

using namespace std::chrono_literals;

class Talker : public rclcpp::Node
{
public:
  explicit Talker(int count)
  : Node("talker"), count_(0), count_limit_(count)
  {
    wait_for_subscriber_ = declare_parameter<bool>("wait_for_subscriber", false);
    publisher_ = create_publisher<std_msgs::msg::String>("chatter", 10);
    timer_ = create_wall_timer(500ms, [this]() {
      if (wait_for_subscriber_ && publisher_->get_subscription_count() == 0) {
        return;
      }
      std_msgs::msg::String message;
      message.data = "hello " + std::to_string(count_);
      publisher_->publish(message);
      RCLCPP_INFO(get_logger(), "publishing: '%s'", message.data.c_str());
      ++count_;
      if (count_ == count_limit_) {
        rclcpp::shutdown();
      }
    });
  }

private:
  rclcpp::Publisher<std_msgs::msg::String>::SharedPtr publisher_;
  rclcpp::TimerBase::SharedPtr timer_;
  bool wait_for_subscriber_{false};
  int count_;
  int count_limit_;
};

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  const auto args = rclcpp::remove_ros_arguments(argc, argv);
  const int count = args.size() > 1 ? std::stoi(args[1]) : 3;
  rclcpp::spin(std::make_shared<Talker>(count));
  rclcpp::shutdown();
  return 0;
}

1.2订阅者

订阅者（subscriber）在话题上注册一个回调。每当消息到达，执行器取出消息 并调用回调；回调返回后，执行器继续等待下一条。订阅者不主动索取消息， 也不控制发布者的节奏。

创建订阅者

create_subscription 的三个参数是话题名、队列深度与回调。 模板参数写明消息类型，回调参数是该消息类型的共享指针： 

subscription_ = create_subscription<std_msgs::msg::String>(
  "chatter", 10, [this](const std_msgs::msg::String::SharedPtr message) {
    RCLCPP_INFO(get_logger(), "I heard: '%s'", message->data.c_str());
  });

回调参数是消息的 SharedPtr，回调期间对象保持有效； 回调返回后指针随参数销毁。需要把消息留到回调之外时，可以在回调里再 保存一份。读取字符串字段时用 message->data，再通过 c_str() 交给 %s。

话题名同样是相对名称，会拼上节点命名空间。发布者与订阅者必须使用同一 话题名与同一消息类型；类型不同时，两端不会建立连接。

启动顺序与回调

默认 QoS 是 volatile：订阅者只收到建立连接之后发布的消息。 先启动订阅者，等一秒让发现完成，再启动发布者；若顺序相反，发布者可能 在订阅者连接前就把三条发完，订阅者只收到剩下的部分。

回调里的计数达到 3 时关闭节点。关闭发生在处理第三条消息的回调里， 因此第三条日志仍会打印；之后的回调不会再执行。两个终端分别运行时， 发布者与订阅者各自结束，命令回到提示符。 

#include <memory>

#include "rclcpp/rclcpp.hpp"
#include "std_msgs/msg/string.hpp"

class Listener : public rclcpp::Node
{
public:
  Listener()
  : Node("listener"), count_(0)
  {
    subscription_ = create_subscription<std_msgs::msg::String>(
      "chatter", 10, [this](const std_msgs::msg::String::SharedPtr message) {
        RCLCPP_INFO(get_logger(), "I heard: '%s'", message->data.c_str());
        ++count_;
        if (count_ == 3) {
          rclcpp::shutdown();
        }
      });
  }

private:
  rclcpp::Subscription<std_msgs::msg::String>::SharedPtr subscription_;
  int count_;
};

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  rclcpp::spin(std::make_shared<Listener>());
  rclcpp::shutdown();
  return 0;
}

1.3自定义消息

标准消息只覆盖常见类型。机器人任务常需要把几个字段放在同一条消息里， 例如目标点的坐标与标签。自定义消息定义在接口包中，由构建工具生成各语言 的头文件，发布者与订阅者再按生成类型使用。

接口包与 .msg

接口包是只放消息、服务与动作定义的普通功能包。文件放在 msg/ 下，每行一个字段，写法是“类型 字段名”。下面定义 Target，包含两个双精度浮点数与一个字符串： 

float64 x
float64 y
string label

字段名由小写字母、数字与下划线组成，不以数字开头。字段类型可以是内置类型 （float64、int32、string 等）， 也可以是其它消息类型或数组。没有赋值的字段在 C++ 对象里是默认值： 数值为 0，字符串为空。

生成头文件

接口包的 CMakeLists.txt 调用 rosidl_generate_interfaces，把 msg/Target.msg 加入生成列表；package.xml 声明 rosidl_default_generators、rosidl_default_runtime 依赖，并加入 rosidl_interface_packages 组。构建后生成 robot_interfaces/msg/target.hpp，C++ 类型是 robot_interfaces::msg::Target。

生成头文件在 install/robot_interfaces/include/ 下。使用它的 节点包必须在 package.xml 中声明 <depend>robot_interfaces</depend>，在 CMakeLists.txt 中 find_package(robot_interfaces REQUIRED)， 并把依赖加到目标上。否则编译时找不到头文件。

发布与读取 Target

发布者的模板参数写成 robot_interfaces::msg::Target， 话题名取 target。每条消息给 x、y 与 label 赋值，再调用 publish。订阅者用同一 类型创建订阅，读取三个字段并打印。 

#include <chrono>
#include <memory>

#include "rclcpp/rclcpp.hpp"
#include "robot_interfaces/msg/target.hpp"

using namespace std::chrono_literals;

class TargetTalker : public rclcpp::Node
{
public:
  TargetTalker()
  : Node("target_talker"), count_(0)
  {
    publisher_ = create_publisher<robot_interfaces::msg::Target>("target", 10);
    timer_ = create_wall_timer(500ms, [this]() {
      const double coordinates[3][2] = {{1.0, 2.0}, {2.5, 3.5}, {4.0, 5.0}};
      const char * labels[3] = {"dock", "aisle", "exit"};

      robot_interfaces::msg::Target target;
      target.x = coordinates[count_][0];
      target.y = coordinates[count_][1];
      target.label = labels[count_];

      publisher_->publish(target);
      RCLCPP_INFO(
        get_logger(), "publishing: label=%s x=%.1f y=%.1f",
        target.label.c_str(), target.x, target.y);
      ++count_;
      if (count_ == 3) {
        rclcpp::shutdown();
      }
    });
  }

private:
  rclcpp::Publisher<robot_interfaces::msg::Target>::SharedPtr publisher_;
  rclcpp::TimerBase::SharedPtr timer_;
  int count_;
};

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  rclcpp::spin(std::make_shared<TargetTalker>());
  rclcpp::shutdown();
  return 0;
}

1.4QoS

QoS（Quality of Service，服务质量）决定发布者与订阅者之间怎样传输消息： 是否重传、保留多少条、晚加入的订阅者能否收到旧消息。两端的 QoS 必须 兼容才能建立连接；不兼容时节点仍会运行，但消息不会送达。

可靠性与历史

可靠性有两种常用取值。reliable 要求中间件在丢失时重传， 适合控制指令与状态；best_effort 不重传，适合高频传感器数据， 丢一帧不影响后续处理。历史策略 keep_last(depth) 只保留最近 depth 条，keep_all 保留全部可用消息。

rclcpp::QoS(10) 默认是 reliable 与 keep_last(10)。链式调用 .best_effort()、.reliable()、 .transient_local() 分别修改对应策略。订阅者与发布者各自 设置，兼容性由中间件按策略组合判断。

兼容性

可靠性的一条基本规则是：best_effort 发布者可以连接 best_effort 订阅者；reliable 发布者可以连接 两种订阅者；best_effort 发布者不能连接 reliable 订阅者。后一种组合中，订阅者要求重传，发布者 不提供重传，中间件拒绝建立连接。

不兼容时两端都会打印 incompatible QoS 警告，并指出 不兼容的策略是 RELIABILITY_QOS_POLICY。看到这条警告， 先核对两端的可靠性设置，而不是检查话题名或域号；话题名与类型都对， 连接仍然不会建立。

例题用到两个程序。发布者 qos_talker 每 500 毫秒发布一条消息， 三条后退出；订阅者 qos_listener 收到消息就打印，并在三秒后 打印总数、停止节点。工作空间里还有一个对照订阅者 qos_listener_best_effort，节点名与类名随程序改变，订阅的 可靠性设为 best_effort，其余与 qos_listener 相同。

持久性与 SensorDataQoS

持久性 transient_local 让发布者保留最近的消息，数量由历史 深度决定；晚加入的订阅者连接后会收到这些消息。默认的 volatile 不保留。发布者与订阅者都设为 transient_local 才会生效。这个策略适合配置、地图或最后 一条状态，不适合连续变化的传感器流。

rclcpp::SensorDataQoS() 是一组预置策略，可靠性为 best_effort，历史深度较小，适合图像、雷达等高频数据。 两端都使用同一个预置时兼容；一端用默认可靠 QoS、另一端用 SensorDataQoS 时，能否连接取决于哪一端是发布者： 可靠发布者可以服务 best_effort 订阅者，反过来不行。

1.5多发布者、多订阅者与消息筛选

一个话题可以连接多个发布者与多个订阅者。发布者之间不互相通信， 订阅者各自收到所有匹配发布者的消息。这一课用命名空间把两个发布者 分到不同话题，再用绝对话题名让订阅者只处理其中一个。

端点计数与命名空间

ros2 topic info 显示话题的发布者数量与订阅者数量。 同一话题上启动两个发布者，计数变成 2；每增加一个订阅者，订阅计数加一。 这些计数是排查“消息有没有人发、有没有人收”的第一项证据。

节点名与话题名是两套名称。节点名由 __node 与 __ns 决定；话题名由 create_publisher 的第一个 参数决定，再拼上节点命名空间。两个节点可以同名；在不同命名空间下 使用相同的相对话题名时，最终的话题完全限定名不同。

回调筛选

筛选发生在订阅者回调内部：回调先检查字段或前缀，不满足就返回。 话题本身仍然传递全部消息，发布者与 ros2 topic echo 看到的 是完整流；只有这个订阅者选择不处理其中一部分。筛选条件写在回调里， 不需要改话题名或 QoS。

练习 1-10

写一个节点名取 prefix_filter 的订阅者，订阅 chatter 话题上的字符串，只打印以 target- 开头的消息，格式为 target: '值'；收到两条后停止。测试时由辅助发布者依次发送 target-alpha、noise、target-beta、noise 2。

[INFO] [prefix_filter]: target: 'target-alpha'
[INFO] [prefix_filter]: target: 'target-beta'
看答案

compare(0, prefix.size(), prefix) 比较字符串开头； 返回值不为 0 就返回，不打印也不计数。收到两个匹配项后关闭。 运行脚本用辅助发布者混发带前缀与不带前缀的四条消息。 

#include <memory>
#include <string>

#include "rclcpp/rclcpp.hpp"
#include "std_msgs/msg/string.hpp"

class PrefixFilter : public rclcpp::Node
{
public:
  PrefixFilter()
  : Node("prefix_filter"), count_(0)
  {
    subscription_ = create_subscription<std_msgs::msg::String>(
      "chatter", 10, [this](const std_msgs::msg::String::SharedPtr message) {
        const std::string prefix = "target-";
        if (message->data.compare(0, prefix.size(), prefix) != 0) {
          return;
        }
        RCLCPP_INFO(get_logger(), "target: '%s'", message->data.c_str());
        ++count_;
        if (count_ == 2) {
          rclcpp::shutdown();
        }
      });
  }

private:
  rclcpp::Subscription<std_msgs::msg::String>::SharedPtr subscription_;
  int count_;
};

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  rclcpp::spin(std::make_shared<PrefixFilter>());
  rclcpp::shutdown();
  return 0;
}

1.6话题诊断

节点不按预期收发消息时，先用命令行确认话题是否存在、类型是否一致、 两端是否连接、消息是否真的在流动。这些检查不改代码，也不依赖发布者 或订阅者的日志。

读话题

ros2 topic list -t 列出话题与类型； ros2 topic info 显示发布者与订阅者数量； ros2 topic echo 打印消息内容。加上 --once 只取一条，加上 --field data 只显示某个字段。

ros2 topic echo 在话题没有发布者时会提示 does not appear to be published yet，然后等待。先确认发布者 已经启动，再看 QoS 与域号；域号不同时，两端在同一台机器上也互相看不见。

频率与排查顺序

ros2 topic hz 统计接收频率，输出平均值、最小与最大间隔、 标准差和窗口内消息数。窗口默认很大，前面的几行可能只覆盖少量消息； 用 --window 10 可以让统计更快稳定。频率受机器负载与调度 影响，数值不必与标称值完全相等。

排查顺序是：先看 list -t 的话题名与类型，再看 info 的端点数量，再看 echo 是否收到消息， 最后用 hz 看节奏。话题名对了但端点为 0，问题在启动、命名 空间或域号；端点存在但收不到，问题多半在 QoS。

例题 · 诊断脚本

脚本启动一个 10 Hz 的 CLI 发布者，依次列出话题、端点、取一条消息， 再保留第一条频率统计。频率与间隔随运行环境变化，下面是一次真实结果。

echo 输出末尾的 --- 是消息分隔符； hz 的 average rate 接近 10， 最小与最大间隔接近 0.1 秒。具体小数位与窗口数每次运行都可能不同。
